# ADR-0059: Markdown file store for memories and documents

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0022 (memory storage), ADR-0036 (automatic memory)
- Related: ADR-0002 (data directory), ADR-0060 (agent definitions)

## Context

Memories are currently stored as text in SQLite. The product owner wants
markdown files under the data directory for both **memories** and **documents**,
with the database keeping only relative references. The file layout must be:

```text
<data>/
  memories/.gitkeep
  documents/.gitkeep
  memories/{agents,projects,lab}/...
  documents/{agents,projects,lab}/...
```

The repository `.data` skeleton tracks only the two `.gitkeep` files; all
imported and generated content is ignored. A Makefile import action must copy a
markdown source into `agent`, `project/<name>`, or `lab/<name>`.

The existing memory UI, prompt context, automatic structural memories, and
deletion paths must continue to work. The database must not retain memory text
after migration.

## Decision

1. **File roots.** The data directory contains `memories/` and `documents/`,
   each with `agents/`, `projects/`, and `lab/` subfolders. The app creates the
   folders with private permissions at startup. Only `.data/memories/.gitkeep`
   and `.data/documents/.gitkeep` are tracked; the rest of both trees is
   ignored.
2. **Relative references.** `memories.path` and `documents.path` store paths
   relative to the data directory, for example
   `memories/projects/portal/1c2d3e4f.md`. Memory content is read from and
   written to the markdown file by the persistence adapter; callers keep the
   existing `MemoryStore` content API.
3. **Migration.** Schema v15 adds `memories.path`. After the schema migration,
   the adapter materializes legacy rows: it writes the content to a markdown
   file, updates the path, and clears the legacy content. A failed write leaves
   the row intact for a later retry. The legacy `content` column is retained
   but always empty after materialization; dropping it is deferred.
4. **Stable entity folders.** `entity_folders` maps `(kind, entity_id)` to a
   unique folder. The folder is a sanitized name; on collision it is suffixed
   with the entity identifier. This keeps readable folders without losing data
   when names repeat.
5. **Confinement and bounds.** Every file operation accepts only a relative path
   with normal components, rejects absolute paths, `..`, symlinks, and paths
   outside the data directory, and bounds memory files to 8 KiB and documents
   to 1 MiB. Writes use a private temporary file and rename.
6. **Documents.** Schema v15 adds `documents` with the same lab/project/agent
   scope shape as memories. The import command copies a UTF-8 `.md` file into
   the matching folder and inserts the relative path and title. The original
   source is not modified.
7. **Makefile import.** `make import SRC=<file.md> INTO=<dest>` accepts
   `INTO=agent` (with `AGENT=<name-or-id>`), `INTO=project/<name>`, or
   `INTO=lab/<name>`. It calls a hidden CLI action; names are resolved
   case-insensitively and ambiguity is an error.
8. **Deletion.** Deleting a memory removes its file. Deleting a project or
   laboratory removes the corresponding entity folders and mapping rows on a
   best-effort basis; agent folders are retained because agent profiles and
   their memories/indexes are preserved on archival.
9. **Tests.** File-store tests cover layout, round-trips, traversal, symlinks,
   markdown-only import, and bounds. Memory tests cover file content and empty
   database content. Document tests cover all destinations, relative paths,
   non-markdown rejection, and unknown/ambiguous names.

## Consequences

- Memory and document content is browsable and versionable as markdown outside
  SQLite, while the database remains the index.
- The migration is incremental and retries failed file writes on the next open.
- The legacy `content` column remains physically present but empty; a future
  schema can drop it after all supported databases are materialized.
- Folder names are sanitized and can gain an ID suffix; the mapping is stable
  even if an entity is renamed.
- Files are local project data: they are not encrypted and are not backed up by
  VLab. The data directory remains private.
- A missing or unreadable memory file is skipped rather than crashing a prompt
  or the memory screen.

## Alternatives considered

- **Keep content in SQLite and add files only for documents**: rejected; the
  product owner explicitly chose migration.
- **Drop `content` in the same migration**: rejected; SQLite cannot write
  external files inside the schema transaction, and a failed write would lose
  data.
- **Use IDs only as folders**: rejected; the product owner preferred readable
  names with an ID suffix on collision.
- **Allow absolute paths in the database**: rejected; references must remain
  relative and confined.
- **Store documents in one flat folder**: rejected; scope folders are required
  for labs, projects, and agents.
- **A document editor in this change**: deferred; import and references are the
  required scope.
