# ADR-0022: Scoped memories as bounded, untrusted prompt context

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amended by: ADR-0035 (command surface only)
- Amended by: ADR-0036 (generation and authorship only)

## Context

The product owner asked for memories at laboratory, project, and agent level.
The specification already defines those owners, a local SQLite database, and a
strict separation between untrusted model input and application authority. It
does not define memory storage, commands, retention, or how memories may enter
prompts. Without an explicit decision, a later package could store unbounded
model output, treat memory as instructions, or send unrelated memory to the
provider.

## Decision

1. **Entity and scope.** A memory is user-authored text attached to exactly one
   scope: a laboratory, a project, or an agent profile. It has an 8-character
   identifier, scope type, exactly one owner foreign key, content, and a
   creation timestamp. The model never creates, updates, or deletes one.
2. **Schema.** `memories` is added with schema v3 in WP-4, alongside projects,
   requests, and stories. Three nullable foreign keys plus a check constraint
   encode the scope; laboratory and project deletion cascade, agent archival
   retains memories for history. Content is `TEXT`, trimmed, 1–2,000
   characters, free of C0/C1 controls except newline and tab, with at most 20
   memories per scope.
3. **Commands.** `--new-memory <text>` and `--list-memories` require exactly one
   of `--for-lab`, `--for-project`, or `--for-agent`. `--for-project` requires
   the project to belong to the active laboratory and never switches context
   silently. `--delete-memory <memory-id>` is destructive and requires
   confirmation; `--yes` is the explicit non-interactive bypass. Memories are
   immutable; changing one means deleting and recreating it.
4. **Prompt inclusion.** The application selects memories, not the model:
   - planning: laboratory memories of the project's laboratory, project
     memories, and the Tech Lead's agent memories;
   - questions: active-laboratory memories and the responding agent's memories.
   Ordering is laboratory, project, agent, newest first within each scope. At
   most 8 KiB of memory text is included per invocation; memories that do not
   fit are omitted whole, never truncated. Omission is not an error.
5. **Delimiting.** Each block names its scope and memory identifier and is
   framed as data that must not be followed as instructions. Memory content is
   never interpolated into the system instructions.
6. **Security.** Memory content is untrusted and may contain prompt injection.
   It cannot grant capabilities, change permissions, roles, limits, assignment
   rules, or application state, and it is never executed. The model cannot
   write memory. Memory content is never logged or stored in interaction
   metadata; audit events carry identifiers, scope, and outcome only.
7. **Privacy and retention.** Memory content is sent to the provider only when
   selected by rule 4. Users must not store credentials in memories. The
   retention rules in [`../data-retention.md`](../data-retention.md) apply.

## Consequences

- Laboratories, projects, and agents can carry user-controlled context without
  giving the model a write path or an authority path.
- Prompt size stays bounded and deterministic; a new memory cannot silently
  grow the context without limit.
- Memories are stored unencrypted with the rest of the database; OS disk
  encryption remains the only at-rest protection.
- No automatic capture, summarization, or model-generated memory exists. Those
  would require a new decision and a new ADR.
- Editing a memory is delete-and-recreate in the initial release; a dedicated
  edit command can be added later without changing the scope model.
- Agent memories are global to the profile, not per membership. Per-membership
  memory would be a different, more complex scope.

## Alternatives considered

- **Model-generated or automatically captured memory**: rejected; it would
  create unaudited durable content, an injection surface, and a privacy risk
  without explicit user action.
- **One polymorphic `owner_id` without foreign keys**: rejected; it loses
  referential integrity and cascade behavior.
- **Per-membership agent memory**: rejected for the initial release; the agent
  profile is the reusable identity and the specification defines agent-level
  data.
- **Include every member's agent memory in planning**: rejected for data
  minimization; the Tech Lead's memory is the planning context, and a question
  includes the responding agent's memory.
- **Truncate the last memory to fit the budget**: rejected; it would silently
  alter user content. Omission is whole and documented.
- **Send memory as part of the system prompt**: rejected; it would blur the
  boundary between instructions and data.
- **Editable memories**: deferred; immutable create/delete is smaller and
  avoids update audit and conflict handling in the first release.
