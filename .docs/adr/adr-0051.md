# ADR-0051: Laboratory metrics dashboard

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0038 (home dashboards and menu), ADR-0043 (board counts)

## Context

The home dashboard lists Laboratories, Projects, Agents, Settings, and the Lab
floor. Card counts are available only inside one project's Kanban board. The
product owner wants a dedicated **Metrics** menu item that shows the state of
the active laboratory at a glance, for example how many cards are open and how
many are closed.

The data already exists: `stories.state` holds `TODO`, `IN_PROGRESS`,
`IN_REVIEW`, `BLOCKED`, or `DONE`, and `requests.status` identifies pending
intake. No new storage is needed. The dashboard must remain read-only and must
not call the provider or trigger a workflow.

## Decision

1. **Menu entry.** The home menu gains a sixth item, **Metrics**, opened with
   `Enter` or the direct key `6`. It is a read-only screen with `r` to reload,
   `?` for help, `Esc` back, and `q` to quit.
2. **Scope.** Metrics cover the active laboratory. The screen shows the
   laboratory name, the number of projects, per-state counts, open, closed,
   total, completion percentage, and pending intake. If an active project
   exists, its row is marked as current.
3. **Definitions.** A card is **open** when its state is `TODO`,
   `IN_PROGRESS`, `IN_REVIEW`, or `BLOCKED`; it is **closed** when its state is
   `DONE`. The total is the sum of all five states. Completion is
   `closed / total`, displayed as a percentage, or `—` when the total is zero.
   Pending intake counts requests in `TODO`, `PLANNING`,
   `NEEDS_CLARIFICATION`, or `FAILED`, matching the board.
4. **Project table.** The screen lists every project in the active laboratory
   with `TODO`, open, closed, and total counts. Projects without stories show
   zeros. Names are sanitized and truncated for the available width.
5. **Read-only.** The screen runs one aggregate query through a new
   `MetricsStore` port. It writes nothing, starts no provider call, and changes
   no story. Reloading re-runs the query.
6. **Empty state.** Without an active laboratory the screen shows an explicit
   empty state with the `Esc` action; it does not fail.
7. **Tests.** A database test covers counts, open/closed totals, pending
   intake, and an empty project. A TUI test opens Metrics from the home menu and
   asserts the rendered counts and labels.

## Consequences

- The operator sees lab-wide progress without opening each board.
- The metrics screen can become long with many projects; the current layout
  shows all rows and relies on the terminal size. Pagination can be added later
  if needed.
- Counts are a snapshot taken at render/reload time; the screen does not live
  update while a workflow runs.
- `open` includes `BLOCKED`: a blocked card is still work that has not been
  accepted.

## Alternatives considered

- **Reuse the Kanban board**: rejected; it is per project and requires opening
  each board.
- **Add a CLI flag**: rejected; the product owner asked for a menu item.
- **Store precomputed metrics**: rejected; it adds write paths and staleness
  for a cheap aggregate query.
- **Show only two numbers (open/closed)**: rejected; per-state counts cost
  nothing and explain the totals.
