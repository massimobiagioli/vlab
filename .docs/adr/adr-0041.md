# ADR-0041: Optional laboratory description and dashboard actions

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0019 (schema v2 extension), ADR-0021 (lab table layout)

## Context

Laboratories currently store only an identifier and name. The product owner
asked for a Description field, an Edit action in the Laboratories dashboard,
and an action that opens the selected laboratory's projects. The description
must survive migration and remain optional for existing rows.

## Decision

1. Add an optional single-line `description` to the laboratory domain and
   `labs` table. It is trimmed, at most 2,000 characters, and control-free;
   an empty value is stored as an empty string and displayed as `—`.
2. Schema v7 adds `description TEXT NOT NULL DEFAULT ''`; existing
   laboratories migrate with an empty description.
3. `app::labs` gains create-with-description and update use cases. `Lab::new`
   remains the name-only constructor and defaults to no description. Updates
   validate the name and description before writing.
4. The Laboratories dashboard shows Description as its own column with dynamic
   widths. The New and Edit actions use a two-field form (Name, Description);
   `Edit` is prefilled from the selected row.
5. The `Projects` action sets the selected laboratory active, clears any
   current project from the previous laboratory, and opens the Projects
   dashboard.
6. Successful create/update/action changes are audited with identifiers only.

## Consequences

- Laboratory context is richer without changing ownership or project rules.
- Existing databases migrate forward with empty descriptions.
- The Labs table loses a dedicated Valid column to make room; invalid
  laboratories are marked with `!` before the name and remain detectable from
  the check action.
- CLI flag creation remains name-only for compatibility; the dashboard exposes
  the description.

## Alternatives considered

- **Required description**: rejected; existing rows and quick creation would
  break.
- **Multi-line text**: rejected for the table and prompt surface; single-line
  is sufficient.
- **Description only in a detail modal**: rejected by the product owner; it
  should be visible in the list.
- **Keep the old New input and add Edit separately**: rejected; a shared
  name/description form keeps behavior consistent.
