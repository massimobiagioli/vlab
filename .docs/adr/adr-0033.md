# ADR-0033: Current project context and project-scoped commands

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amends: ADR-0009 (project command operands only)

## Context

The initial CLI required a project identifier on every project command even
though most workflows operate on one project at a time. The product owner
requires a current project, selected once, so that `--show-project-kanban`,
`--delete-project`, `--assign-agent`, and `--new-request` operate on it without
repeating the identifier. `--open-lab` already selects the current laboratory;
the project selection must be scoped by that laboratory.

## Decision

1. Store the current project in `app_state` under `active_project_id`, next to
   the current laboratory. Both selections are typed, validated identifiers.
2. `--new-project` selects the new project after the project row is committed.
   `--open-project <project-id>` validates that the project belongs to the
   current laboratory and then selects it.
3. `--show-project-kanban`, `--delete-project`, `--assign-agent`, and
   `--new-request` take no project identifier and use the current project.
   `--delete-project` keeps its bound confirmation.
4. A missing or corrupt current project is a missing-context error (exit 3)
   with the hint to list/open projects. Switching laboratories clears the
   project selection because projects are laboratory-scoped.
5. Deleting the current project clears the selection. Deleting a laboratory
   clears the selection as well.
6. `--new-request` accepts only request text (literal or piped stdin); the
   current project supplies the target.

## Consequences

- Short commands for the common single-project workflow.
- Existing scripts that pass a project identifier must switch to
  `--open-project` once and then use the project-scoped commands.
- A project selection can become stale if the project is deleted outside VLab;
  the next command reports the missing project instead of acting on another.
- The state remains content-free: two short identifiers in `app_state`.

## Alternatives considered

- **Keep explicit identifiers**: rejected by the product owner; repetitive for
  the intended workflow.
- **Infer the project from the last request**: rejected; implicit and unstable.
- **Store the project name**: rejected; identifiers are the established key.
