# ADR-0024: Bound confirmations and the active-planning deletion guard

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

WP-4 introduces destructive operations for laboratories, projects, agents, and
memories. Specification §6.4, §7.3, §8.3, and §13 require explicit
confirmation, atomic cascades, preservation of agent profiles, and refusal
while planning is active. A-08 defines `y/N` confirmation with an explicit
`--yes` bypass and fail-closed behavior without a terminal. A-11 defines the
single-process planning lease.

## Decision

1. **Confirmation request.** A destructive command builds a concrete summary
   with the entity identifier, name, and affected counts (projects, requests,
   stories, memberships, memories, assigned stories) from a preflight query.
2. **Prompt behavior.** On a terminal, show the summary and ask `y/N`,
   defaulting to no. `--yes` skips only the prompt for commands that declare
   support. Without a terminal and without `--yes`, exit 4; a declined answer
   or EOF exits 5 and changes nothing.
3. **Snapshot binding.** The deletion re-reads the plan inside its transaction
   and compares it with the confirmed plan. A changed name or affected count
   aborts with exit 4 rather than deleting different data.
4. **Cascades.** Laboratory deletion removes projects, requests, stories,
   memories, and memberships in one transaction and clears a matching active
   selection. Project deletion removes its requests, stories, and memories.
   Agent deletion archives the profile, removes memberships, preserves story
   references and memories, and warns when the agent is a Tech Lead.
5. **Active-planning guard.** A request with status `PLANNING` and a
   `planning_started_at` within the 240-second lease blocks deletion of its
   project, its laboratory, and agents that are members of a laboratory with
   such a request. A stale lease does not block. The guard reads only local
   data and performs no provider call.
6. **Unfinished work.** Agent deletion is blocked when any assigned story is
   not `DONE`.
7. **Audit.** Successful deletions emit `lab_deleted`, `project_deleted`, and
   `agent_archived`; memory deletion emits `memory_deleted`. Events carry
   identifiers and outcomes only.

## Consequences

- Destructive commands cannot silently delete a different snapshot than the
  one the user confirmed.
- Scripts need `--yes`; accidental non-interactive deletion fails closed.
- The guard is conservative and single-process. A long-running operation in
  another process is not detectable, which is documented as a limitation.
- Archived agents remain in the database and in story references, preserving
  history; they are excluded from lists and prompt rosters.

## Alternatives considered

- **Delete without a plan snapshot**: rejected; confirmation could describe
  one thing and delete another.
- **Prompt even with `--yes`**: rejected by A-08; scripts need an explicit
  bypass.
- **Hard-delete agents**: rejected; A-15 requires historical identity.
- **Use a global time-based lock file**: rejected for the initial release;
  the single-process assumption plus the request lease is simpler.
- **Delete memories with agents**: rejected; memories are historical context
  for archived profiles and are not used in prompts.
