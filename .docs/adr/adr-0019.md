# ADR-0019: Schema v2 for laboratories, agents, and memberships

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

WP-3 introduces the first domain entities. `ADR-0002` and `ADR-0016` fix the
storage technology, connection policy, and schema v1. The specification §3.1
and §3.3 define laboratories, agents, roles, skills, and memberships; §6.5
requires structural validation; A-22 allows an agent to belong to several
laboratories with at most one `lead` per laboratory. The plan requires schema
v2, constraints, cascades, and preservation of schema v1 data.

## Decision

1. **Tables.** `migrations/0002_labs_agents.sql` adds three `STRICT` tables:
   - `labs(id, name, created_at, updated_at)` with a trimmed 1–100 character
     name check;
   - `agents(id, name, role, description, skills_json, provider, model, cv,
     archived_at, created_at, updated_at)` with a role check for `lead`,
     `dev`, `analyst`, `qa` and the same name check;
   - `lab_memberships(lab_id, agent_id, joined_at)` with foreign keys to both
     tables, `ON DELETE CASCADE`, and a composite primary key.
2. **Indexes.** The membership primary key covers laboratory lookups; an index
   on `agent_id` covers reverse lookups; a partial index on `archived_at`
   covers active agents.
3. **Skills.** `skills_json` stores a JSON array of lowercase slug tags. The
   domain grammar (`[a-z0-9-]{1,32}`, at most 20, deduplicated) makes escaping
   unnecessary, so a small audited encoder/decoder is used instead of adding
   `serde_json` before WP-5. Decoding rejects anything outside that grammar.
4. **One Tech Lead.** The rule spans `agents.role` and `lab_memberships`, so a
   SQLite unique index cannot express it without duplicating the role. It is
   enforced by the application before insert (and reported by `--check-lab` if
   stored data is changed out of band). The single-process operation model
   makes this sufficient; WP-4 deletions revisit the rule.
5. **Cascade and preservation.** Deleting a laboratory removes its
   memberships; agent profiles remain reusable. Migration from v1 preserves
   `app_state` and `events`, and the migration test applies v1, writes state,
   then applies v2.
6. **Timestamps.** `created_at`, `updated_at`, and `joined_at` are generated
   by SQLite in RFC 3339 UTC, continuing ADR-0016.
7. **No credentials, prompts, or CVs of third parties.** `cv` is optional
   user-provided profile text and is never sent to the provider (A-13). No
   column stores credentials or provider payloads; the schema policy test
   extends to the new tables.

## Consequences

- Laboratories, agent profiles, and memberships have referential integrity and
  deterministic ordering.
- Membership cascades keep the database consistent; preserving agent profiles
  matches the specification's reusable-agent model.
- The one-lead rule is not enforced by SQL. `--check-lab` reports violations
  and the wizard refuses a second lead before writing; a direct database edit
  can still violate it, which is documented as an operational limitation.
- The JSON storage format is project-specific but tiny and strictly validated.
- Adding columns or indexes requires a new migration and an update to
  [`../data-retention.md`](../data-retention.md).

## Alternatives considered

- **Store skills in a child table**: rejected for WP-3; a bounded array is
  simpler and the data is always read with the profile. A future query need
  can add a table with a migration.
- **Add `role` to memberships**: rejected; the role belongs to the reusable
  agent profile, and duplicating it would create two sources of truth.
- **Enforce one lead with a trigger**: rejected as harder to test and reason
  about than an application check plus a validation report.
- **`serde_json` now**: rejected by the incremental dependency rule
  (ADR-0008); the tag grammar needs no general JSON parser.
- **Use `WITHOUT ROWID`**: rejected; no measured need, and it complicates
  future schema changes.
