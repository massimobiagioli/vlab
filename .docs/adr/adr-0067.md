# ADR-0067: Autonomous remediation of blocked stories

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0050 (workflow), ADR-0023 (story lifecycle), ADR-0026 (provider)

## Context

The workflow marked a story `BLOCKED` after three failed attempts or a rejected
review. A blocked card then waited for a human action: no agent added context,
made a technical decision, or put it back in progress. VLab is an autonomous
team; its flow must continue and cards must reach `DONE` without manual
intervention. The Tech Lead is the role that owns technical decisions.

## Decision

1. The Tech Lead autonomously remediates `BLOCKED` stories. For each blocked
   story it receives the original request, story, acceptance criteria, previous
   work/review outcome, previous Tech Lead context, and the active roster, and
   returns a strict decision object: a technical decision, concrete context for
   the next attempt, and an active roster agent to execute it.
2. The application validates the decision and assignee locally. An invalid or
   unavailable model decision falls back to a bounded retry instruction and a
   valid rostered agent. The model never chooses a state transition or grants
   permissions.
3. Remediation persists a bounded `tech_lead_context`, reassigns the story,
   resets the execution attempt counter, increments `remediation_attempts`,
   removes the stale outcome, and moves the story to `IN_PROGRESS`. The next
   execution prompt includes the Tech Lead context as untrusted data.
4. The workflow pass remediates blocked stories and retries them in the same
   pass, up to three remediation attempts per story and a bounded workflow
   deadline. A story that still cannot finish remains `BLOCKED` with its
   history; it is never silently marked `DONE`.
5. Schema v16 adds `stories.remediation_attempts` and
   `stories.tech_lead_context`. No other table, dependency, provider contract,
   or trust boundary changes.
6. A successful remediation records a content-free `story_remediated` event.
   The execution/review events remain unchanged.
7. Tests cover exhausted attempts, rejected review, reassignment, persisted
   context, the remediation prompt, and the normal DONE path.

## Consequences

- A blocked story is retried by the team instead of waiting for an operator.
- Remediation can assign a different active agent when the current one is not
  making progress.
- Up to three additional bounded remediation cycles per story are possible;
  each is visible through events and the stored context.
- A genuinely impossible story can still remain `BLOCKED`; claiming `DONE`
  without evidence is forbidden.
- The migration adds two columns and extends the story detail with Tech Lead
  context.

## Alternatives considered

- **Leave `BLOCKED` as a terminal state**: rejected by the product owner; it
  stops the autonomous flow.
- **Immediately mark blocked stories `DONE`**: rejected; it would fabricate
  completion and violate the evidence rules.
- **Retry the same prompt without a Tech Lead decision**: rejected; it repeats
  the failure without new context.
- **Let the model choose state transitions or permissions**: rejected; the
  application owns state and authorization.
- **Unbounded remediation**: rejected; it can loop forever and spend unbounded
  provider budget.
