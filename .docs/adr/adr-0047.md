# ADR-0047: Assigned stories start in IN PROGRESS

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0023 (initial story state), ADR-0043 (board interpretation)

## Context

Planning creates stories from a natural-language request. The Tech Lead may
assign a story to an active project member, and the current implementation
stores every story as `TODO` (ADR-0023, TECHNICAL-SPECIFICATIONS §9.3). The
product owner expects a story with an owner to appear in `IN PROGRESS`
immediately on the board; keeping it in `TODO` looks like the assignment was
ignored.

VLab still has no execution engine and the board remains read-only. The change
therefore redefines `IN PROGRESS` for this product stage as "assigned and ready
to be worked", not "an agent process is running". Unassigned stories stay in
`TODO` until an owner is chosen.

## Decision

1. **Initial state.** When planning commits its stories in one transaction, a
   story with `assigned_agent_id` is inserted as `IN_PROGRESS`. A story with no
   assignee is inserted as `TODO`.
2. **Owner of the rule.** The application layer exposes the policy as
   `PlannedStoryRow::initial_state`; the SQLite adapter binds the resulting
   state in the existing insert. The state is not inferred by SQL or by the
   dashboard.
3. **Board.** The Kanban board remains read-only: it renders the stored states
   and does not introduce manual transitions. `IN PROGRESS` means the story
   has an owner; it does not claim that an agent process is running.
4. **No other transitions.** `IN_REVIEW`, `BLOCKED`, and `DONE` remain unused
   by planning. A future execution workflow may add explicit transitions and
   must record a new decision.
5. **Existing rows.** Schema v8 adds a one-time data migration that moves
   existing `TODO` stories with an assignee to `IN_PROGRESS`; unassigned stories
   remain `TODO`. No table or column changes, provider changes, or dependency
   changes are introduced. The request itself remains an intake item; counts on
   the project and Kanban views derive from the stored state as before.
6. **Tests.** Planning tests cover an assigned story (`IN_PROGRESS`), an
   unassigned story (`TODO`), and the absence of partial commits.

## Consequences

- The board immediately reflects the Tech Lead's assignment.
- `TODO` can be empty after planning when every story has an owner. That is
  expected: the intake item remains visible separately.
- `IN PROGRESS` is an assignment/readiness state in this release, not evidence
  of running work. Documentation and the dashboard hint must say so.
- Users still cannot move a story manually; that remains a future execution
  feature.

## Alternatives considered

- **Keep every story in TODO**: rejected by the product owner; it hides the
  assignment decision.
- **Move every story to IN PROGRESS**: rejected; an unassigned story has no
  owner and belongs in TODO.
- **Add a manual Start action now**: deferred; it is a different product
  decision and would still require a separate owner/readiness model.
- **Add a READY state**: rejected for this change; it requires a schema and
  board change and duplicates `IN_PROGRESS` for the current stage.
