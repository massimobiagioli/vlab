# ADR-0049: Automatic workflow resume on startup and application logs

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0048 (workflow trigger and recovery), ADR-0011 (audit event
  visibility), ADR-0009 (flag surface)

## Context

ADR-0048 introduced the bounded, no-tool work/review simulation and exposed a
hidden `--run-workflow` flag as its recovery path. The product owner does not
want the recovery path to be a manual user step: the workflow must resume by
itself when the application starts, just as it already does after planning.

The product owner also asked for a way to inspect what the application did:
`vlab --logs`. Until now, audit events were persisted but only visible through
SQLite or `RUST_LOG` diagnostics. Diagnostics are intentionally off by default
and carry tracing detail; the audit events are the durable, content-free record
of actions, so they are the right source for a user-facing log view.

## Decision

1. **Startup resume.** When the interactive entry point starts (stdin and
   stdout are terminals) and an active project exists, the application runs the
   same bounded workflow as a planning run before opening the dashboard.
   Pending `IN_PROGRESS` or `IN_REVIEW` stories without an outcome are
   processed. The workflow is not a navigation action and has no dashboard
   keybinding.
2. **No manual workflow flag.** The hidden `--run-workflow` flag and its
   `Action` variant are removed. A provider failure is retried by the next
   startup or planning run; there is no separate command to remember.
3. **Failure isolation.** A missing active project, unreadable settings, a
   missing provider configuration, or a workflow error skips or warns but never
   blocks the dashboard. The existing planning path is unchanged and still
   reports the workflow summary in its outcome.
4. **`--logs`.** `vlab --logs` prints the newest 100 audit events, newest first,
   as a table: timestamp, kind, outcome, entity type and identifier, and error
   code. It reads the existing `events` table, adds no schema change, and adds
   no content: no prompt, response, story text, request text, memory content,
   CV, or credential can appear because the audit event type has no free-text
   field (ADR-0011).
5. **Hidden flag.** `--logs` is a hidden legacy-style flag like the other
   two-dash commands (ADR-0009); the primary entry point remains the bare
   `vlab` dashboard.
6. **Tests.** A CLI test creates a laboratory and asserts that `--logs` shows
   `lab_created`/`memory_created` while containing neither the laboratory name
   nor a credential marker.

## Consequences

- The operator no longer needs a recovery command; starting the application is
  enough.
- Starting the application can perform provider calls when pending stories
  exist, with the ADR-0048 bounds (two calls per story, one attempt each,
  60-second call timeout, 512 output tokens, 240-second total deadline).
- `--logs` exposes only the content-free audit metadata already stored; it is
  not a replacement for `RUST_LOG` diagnostics.
- Removing `--run-workflow` is a CLI contract change; scripts that used it must
  rely on startup or run a planning request instead.

## Alternatives considered

- **Keep `--run-workflow` as a hidden recovery flag**: rejected by the product
  owner; it makes recovery a manual step.
- **Resume from a dashboard action**: rejected; the workflow must be automatic
  and not depend on navigation.
- **Make `--logs` read `RUST_LOG` diagnostics**: rejected; diagnostics are off
  by default, are not persisted, and may contain free-form messages. The audit
  events are the durable, typed, content-free record.
- **Add a `logs` table**: rejected; the `events` table already holds exactly the
  required fields.
