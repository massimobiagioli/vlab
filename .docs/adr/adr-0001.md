# ADR-0001: Rust modular monolith with explicit layer boundaries

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

The project is a local, text-only command-line application. It must persist
domain data locally, call one remote AI provider over HTTPS, and keep model
output strictly outside the authorization and execution path.

`ARCHITECTURE.md` requires a single process, deterministic control flow,
bounded execution, and no multi-agent orchestration. `STACK.md` prohibits an
HTTP server, a web GUI, a general-purpose agent framework, and distributed
execution for the initial scope. `CONSTITUTION.md` requires safe, idiomatic
Rust, narrow interfaces, and testable behavior.

## Decision

1. Implement the application as one Rust binary named `vlab`, built with the
   pinned stable toolchain recorded in `rust-toolchain.toml`.
2. Use a modular monolith with these layers and a single dependency direction:

   ```text
   cli -> app -> domain
                 ^
                 |
              infra (implements ports declared for app/domain)
   ```

   - `domain`: pure rules, validation, value types, and typed errors. No
     `sqlx`, `reqwest`, `clap`, filesystem, or network access.
   - `app`: use cases, orchestration, transaction boundaries, and policy
     enforcement.
   - `infra`: SQLite repositories, configuration files, and provider adapters.
   - `cli`: argument parsing, input handling, rendering, and exit-code mapping.
   - `obs`: structured diagnostics and audit-event emission.
3. Keep the process single-tenant and single-user. Do not introduce an HTTP
   server, a full-screen TUI framework, a plugin system, or a distributed task
   queue.
4. Do not introduce an agent framework. Model-backed behavior is limited to
   explicitly bounded operations implemented in application code; the model
   proposes data, it never grants permissions or executes actions.
5. Prefer safe Rust. Add `#![forbid(unsafe_code)]` at the crate root unless a
   later ADR justifies, isolates, and reviews an exception.
6. Use `thiserror` for domain and module errors and `anyhow` only at the
   application boundary for contextual reporting.

## Consequences

### Positive

- Small dependency surface, fast builds, and simple local deployment.
- Domain rules are unit-testable without I/O.
- Provider and storage are replaceable behind narrow ports.
- Security boundaries remain visible in code structure.

### Negative / trade-offs

- All wiring is manual; there is no framework to generate adapters.
- The single binary cannot scale horizontally, which is acceptable for a local
  CLI.
- Layer discipline must be reviewed; the compiler cannot enforce every
  forbidden import.

## Alternatives considered

- **Agent framework**: rejected because `ARCHITECTURE.md` and `STACK.md`
  prohibit it for the initial scope and it would obscure control flow.
- **Microservices or an HTTP API**: rejected because there is no multi-user or
  remote-access requirement.
- **Full-screen TUI**: rejected because the required interface is line-oriented
  and scriptable.
