# ADR-0062: Fixed three-room MSX floor with bidirectional Kanban

- Status: Accepted
- Date: 2026-11-17
- Supersedes: ADR-0045 (read-only laboratory floor view)
- Superseded by: —
- Amends: ADR-0038 (dashboards), ADR-0043 (Kanban screen), ADR-0034
  (project roster)

## Context

The first laboratory floor grouped agents into dynamic project pods. It was
readable but not a laboratory: rooms were essentially empty lists, the layout
changed with the project count, and the screen did not show the work that the
agents were doing. The product owner wants a fixed, recognizable MSX
laboratory with three rooms, desks and decorations, visible movement and
interactions between agents, and a direct two-way link with the active
project's Kanban board. The floor must stay useful rather than decorative:
task context and the selected agent's current work must be visible.

ADR-0045 deliberately rejected animation and fixed rooms to keep the scene
deterministic and cheap. That trade-off no longer matches the requirement. A
new decision is needed for a deterministic, bounded animation model and a
stable room layout.

## Decision

1. **Design skill.** Add the portable
   `msx-computer-senior-software-architect` skill for MSX graphics, VDP-era
   sprite/tile thinking, game loops, and their translation into safe Rust and
   `ratatui`. It records the visual and engineering conventions used by the
   floor.
2. **Fixed three-room plan.** The floor is one stable laboratory plan with a
   **Project Lab**, a **War Room**, and a **Lounge**, connected by a bottom
   corridor. The rooms do not paginate or change position. At the 60×20
   minimum they remain three readable rooms; wider terminals add content, not
   a different topology.
3. **Active project.** The Project Lab is the active project. It shows the
   project name, its open tasks and states, desks, a terminal, and a board. If
   no project is active, the room explains that and points to the Projects
   dashboard. The floor reads the project from stored application state; it
   never guesses from a story.
4. **Agent placement.** The Tech Lead is in the War Room. An agent with two or
   more open tasks is focused there. A working member of the active project is
   in the Project Lab. Every other active agent is in the Lounge. Each active
   agent appears exactly once. Archived agents are counted but hidden.
5. **Real task context.** The read model includes open stories for the active
   project and for each agent: identifier, project, title, state, priority, and
   due date. The Project Lab board shows the active project's tasks; the
   selected agent's status line shows the current task; `Enter` opens the
   existing agent detail with a `Working on` section; `t` opens the selected
   agent's first task as the existing read-only story detail.
6. **Deterministic movement.** A presentation tick drives bounded tours derived
   from `(tick, stable_hash(agent_id))`. A working agent alternates between a
   desk and the board; a worker may walk to the War Room to coordinate with the
   lead; focused agents use focus desks; idle agents wander between Lounge
   spots. Movement follows the corridor through room doors. No wall-clock
   time, random source, thread scheduling, provider call, or database write
   affects the scene. The tick is reset when the view is recreated and is not
   persisted.
7. **Interactions.** Agents in the same room with different roles may show a
   deterministic connector and alternating `( ? )`/`( ! )` bubbles, matching
   the existing exchange metaphor. Idle agents show `(zzz)`. The legend and
   labels carry the meaning; color is never the only signal. The scene is
   explicitly an overview of stored assignments, not a live message trace.
8. **Visual language.** Double outer frame, inverted title bar, `MSX` badge,
   tiled floors, block sprites at wide sizes and one-line sprites at narrow
   sizes, per-room accent colors, task cards, desks, whiteboard, coffee
   machine, plant, couch, and a corridor with doors. The MSX palette is
   approximated with semantic terminal colors and text fallbacks.
9. **Bidirectional link.** `f` opens the active project's Kanban from the
   floor and the active project's floor from the Kanban. `Esc` returns to the
   screen that opened the current view. The Kanban action bar and help expose
   the link. Opening the board from the floor must not lose the floor's
   selected agent or the board's column.
10. **Bounds and security.** No schema, migration, dependency, provider
    contract, or trust-boundary change. The floor remains read-only; task
    titles and request text are sanitized terminal data, never executed or
    logged. Animation work is bounded by room count, agent count, and tour
    length. Frame rate is low and redraws happen only while the floor is
    visible.
11. **Tests.** Unit tests cover room assignment, task attachment, deterministic
    movement between rooms, interactions, and empty states. Renderer tests
    cover 60×20, 80×24, and 100×30, ASCII/no-color, the three rooms,
    decorations, task board, status line, and both link directions.

## Consequences

- The floor is recognizable at a glance and stable across laboratories; users
  learn one room layout.
- The active project becomes the focus; other projects are reachable through
  the Projects dashboard rather than spread across the floor.
- Movement and interaction are presentation only. They must never be read as
  live provider execution or inter-agent messaging.
- The floor and Kanban become a two-screen workspace, so return-path state is
  part of the TUI state machine.
- Additional read queries per floor reload are bounded and read-only.

## Alternatives considered

- **Keep dynamic project pods**: rejected; rooms are not recognizable and the
  layout grows without limit.
- **One room per project**: rejected; the requirement fixes three rooms and a
  single active project is the useful focus.
- **Static agents, no movement**: rejected by the product owner; movement is
  part of the requested experience.
- **Wall-clock animation or an animation crate**: rejected; non-deterministic,
  hard to test, and unnecessary for a character grid.
- **Persist animation state or interactions**: rejected; no product value and
  it would add retention and privacy surface.
- **Derive interactions from provider metadata**: rejected; that metadata is
  content-free and not attributable to agent pairs.
