# ADR-0055: Larger preset catalog and populate profile preview

- Status: Accepted
- Date: 2026-11-16
- Supersedes: —
- Superseded by: —
- Amends: ADR-0052 (catalog size), ADR-0053 (populate screen)

## Context

ADR-0052 introduced a bounded preset catalog and ADR-0053 added the two-pane
populate screen. The product owner now wants twenty additional fictional
agents, for a total of thirty, with Japanese, Greek, and Slavic name
inspirations from the 1960s–1980s, including female profiles. The catalog limit
of twenty would reject the expanded file.

The populate screen shows a compact row per agent: name, role, and a truncated
profile description. The operator cannot read the full description or skill
list before moving an agent, so choosing the right profile requires an extra
step outside the screen. The screen needs a read-only detail action that does
not change membership.

## Decision

1. **Catalog bound.** Raise `PRESET_MAX_AGENTS` from 20 to 50. The file remains
   capped at 512 KiB, each agent keeps the existing name, description, skill,
   and CV limits, and the roster still requires exactly one `lead`. The loader
   remains idempotent by name.
2. **Catalog content.** `assets/agents.yaml` grows to thirty fictional agents.
   The additions mix Japanese, Greek, and Slavic first and last names from the
   1960s–1980s, including female names, and cover backend, frontend, mobile,
   data, platform, design, research, testing, security, and analysis skills.
   No name refers to a real player.
3. **Profile preview.** The populate screen gains a `v` action for the selected
   agent in either pane. It opens a read-only dialog with the agent's full
   description, role, skills, status, memory count, and project associations
   through the existing `agents::detail` use case. It never changes membership,
   writes data, or calls the provider.
4. **Controls and help.** The populate action bar and help list `v` as
   **Details**. Moving with `Enter`/`Space` and saving with `s` are unchanged.
5. **Tests.** The tracked-catalog test asserts thirty entries and the role mix.
   The populate render test asserts the details action; a dashboard test opens
   the dialog from a selected available agent and verifies the full
   description. Existing move/save and lead-validation tests remain.

## Consequences

- The catalog can grow to fifty profiles without a new parser or schema change.
- A larger catalog needs scrolling in the populate screen; the existing page
  and selection handling already supports it.
- The detail dialog is informational; the operator still moves and saves
  explicitly.
- The loader time and output grow with the catalog, bounded by the file cap and
  the fifty-agent limit.

## Alternatives considered

- **Keep the twenty-agent limit and split the file**: rejected; the product
  owner wants one tracked catalog and the loader already handles a bounded list.
- **Show the full description in every row**: rejected; it makes rows tall and
  the two-pane layout hard to scan.
- **Use `Enter` for details instead of moving**: rejected; moving is the
  primary action and changing it would break the established controls.
- **Reuse the CLI list output**: rejected; it lacks the full profile fields and
  would leave the dashboard.
