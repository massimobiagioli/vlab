# ADR-0066: Autonomous clarification resolution

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0026 (planning contract), ADR-0003 (bounded provider), ADR-0023
  (request lifecycle)

## Context

The planning prompt allowed the Tech Lead to return `clarification_questions`.
The application persisted the request as `NEEDS_CLARIFICATION` and asked the
operator for answers. VLab is a team of autonomous agents: the human is not in
the loop, cannot answer those questions, and expects the agents to continue
working the board. A request that stops for human input leaves the Kanban
without cards and contradicts the product model.

## Decision

1. New requests never stop at `NEEDS_CLARIFICATION`. The Tech Lead owns
   ambiguity resolution and must produce a plan with its own explicit
   assumptions.
2. The initial prompt states that no human is available and that the Tech Lead
   must resolve ambiguity itself.
3. If the model still returns questions, the application makes up to two
   bounded clarification calls. Each call receives the original request,
   roster, bounded memories, and the open questions, and must return a strict
   schema-version-1 plan with `clarification_questions` empty. The questions and
   output are untrusted data and are validated locally.
4. Each clarification call uses one provider attempt, a 90-second deadline, the
   same model, output-token cap, cancellation token, and content-free events as
   planning. There is no unbounded repair loop.
5. A resolved plan continues through the normal rules, persistence, and bounded
   workflow. If the questions remain after two calls, the request is `FAILED`
   with the stable code `clarification_unresolved`; the application does not ask
   the human or create a partial story set.
6. `NEEDS_CLARIFICATION` remains a valid stored status for legacy rows and
   read models, but new planning never writes it.
7. No schema, dependency, or trust-boundary change. The clarification calls are
   additional bounded provider calls, not tools or autonomous execution.

## Consequences

- A request produces cards without human input, so the team can keep working.
- Planning may cost up to three provider calls instead of one; each is bounded
  and recorded through the existing invocation/event path.
- An unresolved request fails visibly with `clarification_unresolved` instead of
  silently waiting for an operator.
- The request detail and interaction history remain compatible with legacy
  clarification rows.

## Alternatives considered

- **Ask the human**: rejected; the human is not in the loop.
- **Ignore questions and persist no stories**: rejected; it leaves the board
  empty.
- **Unbounded clarification loop**: rejected; cost and failure modes are
  unbounded.
- **Remove clarification questions from the schema**: rejected; it would turn a
  clarification into a generic validation failure and lose the useful feedback.
- **Persist questions as a TODO story**: rejected; a question is not a
  software story, and it does not produce the requested work.
