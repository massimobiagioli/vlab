# ADR-0030: Credentials in the private settings file

- Status: Accepted
- Date: 2026-11-12
- Supersedes: ADR-0015
- Superseded by: —
- Amends: ADR-0002, ADR-0003, ADR-0014, ADR-0025, ADR-0026 (credential source
  and tracked example only)

## Context

ADR-0015 and the specification required credentials to be read only from the
`DEEPSEEK_API_KEY` and `GITHUB_API_KEY` environment variables and explicitly
forbade them in `settings.yaml`. On 2026-11-12 the product owner reversed that
rule: the settings file is the credential store, it must stay outside version
control, and the development data directory must provide a
`settings.example.yaml` template. The environment-variable contract is
therefore no longer valid and the specification, code, tests, and documentation
must agree on the new source.

The existing privacy controls remain mandatory: the file is already private,
the parser is strict, errors are content-free, and credentials must never reach
the database, logs, prompts, errors, events, or command output.

## Decision

1. **Credential section.** `settings.yaml` accepts an optional `credentials`
   mapping with two optional fields:
   `deepseek_api_key` (required for planning and questions) and
   `github_api_key` (required only for projects created with
   `--github-source`).
2. **Validation.** Each supplied key is trimmed, must be a non-empty token of at
   most 512 bytes, and must contain no whitespace or control characters.
   Invalid values fail configuration parsing without echoing the value. Unknown
   fields inside `credentials` are rejected like any other unknown field.
3. **Sole source.** Application behavior reads credentials only from the parsed
   settings document. `DEEPSEEK_API_KEY` and `GITHUB_API_KEY` are not consulted
   at runtime. Tests and fixtures use synthetic keys in settings files.
4. **Privacy.** `settings.yaml` stays in the per-user configuration directory,
   is written with mode `0600`, and its directory with mode `0700`. On Unix,
   loading refuses a file readable by group or other users and reports the
   `chmod 600` remedy instead of reading it. The file remains outside version
   control. `Debug` output for settings and credentials prints
   `[REDACTED]`, never a value. `--show-settings` reports only `set`/`unset`.
   Credentials are never written to the database, events, interaction metadata,
   prompts, logs, errors, or command output.
5. **Redaction checks.** Request text, questions, memory content, and provider
   responses are compared with the configured DeepSeek key and rejected when
   they contain it, without persisting or displaying either value.
6. **Example template.** The development data directory contains a tracked
   `.data/settings.example.yaml` with placeholders. It is not loaded
   automatically: the user copies it to `settings.yaml`. The `--edit-settings`
   draft template also shows the credential fields.
7. **Retained decisions.** All other decisions of ADR-0015 remain in force:
   strict parsing, content-free errors, atomic editing, private drafts,
   fail-closed directory permissions, and no provider or database side effects
   from settings commands. The environment-source clauses of ADR-0002,
   ADR-0003, ADR-0025, and ADR-0026 are amended accordingly.

## Consequences

- One file now holds configuration and credentials, so backups, editor
  backups, and screen sharing can disclose keys. The private permissions,
  redaction, and the version-control exclusion mitigate this, but users must
  protect the file like any other secret.
- Credential rotation is an edit of `settings.yaml`; no restart or environment
  change is needed.
- The example file makes the expected shape discoverable on a fresh clone
  without containing a real secret.
- A settings file copied from the example is not invoked automatically, so a
  missing key still fails closed with an actionable hint instead of a silent
  default.
- Environment-based deployment convenience is intentionally lost; it can be
  reintroduced only by a new ADR.

## Alternatives considered

- **Keep environment variables**: rejected by the product owner on
  2026-11-12.
- **Separate `credentials.yaml`**: rejected; it adds a second private file and
  a second path-resolution and permission surface without a security gain.
- **Operating-system keyring**: deferred; it adds a platform dependency and
  interactive behaviour that the initial local CLI does not require.
- **Store credentials in the database**: rejected; it mixes secrets with
  project data, complicates deletion and backup, and contradicts data
  minimization.
- **Loose parsing with empty-string defaults**: rejected; values would be
  ambiguous and errors less specific.
