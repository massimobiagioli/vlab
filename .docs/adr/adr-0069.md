# ADR-0069: Close exhausted stories with a Tech Lead compromise and technical debt

- Status: Accepted
- Date: 2026-11-17
- Supersedes: ADR-0067 (autonomous remediation of blocked stories)
- Superseded by: —
- Amends: ADR-0050 (bounded workflow), ADR-0023 (story lifecycle),
  ADR-0026 (provider contract), ADR-0051 (laboratory metrics)

## Context

ADR-0067 let the Tech Lead remediate a `BLOCKED` story, but it kept two
problems. When the remediation budget was exhausted the story remained
`BLOCKED`, so the autonomous flow still needed a human. Worse, execution and
remediation could alternately set the story `IN_PROGRESS` and `BLOCKED`, making
the card bounce between two Kanban columns instead of reaching a conclusion.

The product owner requires the Tech Lead to reach a decision even when it is
uncomfortable: accept the best available result, close the card, and open a
separate card for the residual technical debt. A card must never oscillate
between columns.

## Decision

1. The automatic workflow never produces the `BLOCKED` state. `BLOCKED` remains
   a valid stored state for historical rows and a possible manual label, but no
   workflow branch sets it.
2. A story has two bounded budgets: three execution attempts per remediation
   cycle and three remediation cycles. When execution attempts are exhausted or
   a review is rejected, the next workflow round selects the story for Tech Lead
   remediation without changing its column.
3. After the last remediation cycle the Tech Lead makes a closing decision. One
   bounded provider call returns strict JSON with `decision` (the compromise
   and what is accepted) and `debt_context` (the residual work). Invalid output
   or an unavailable provider falls back to a deterministic, bounded decision.
4. The original story closes as `DONE` in a single transaction:
   - the stored outcome keeps the last work summary and branch/commit evidence;
   - the review outcome records the `Tech Lead compromise:` decision;
   - the reviewer is the Tech Lead, and the decision is stored as the final
     `tech_lead_context`.
   The `DONE` state therefore rests on recorded work and a recorded closing
   review, never on a fabricated success.
5. The same transaction creates one technical-debt follow-up card linked through
   `stories.debt_of_story_id`. It is a normal `TODO` story, unassigned so it is
   not executed immediately, with a deterministic title
   (`Technical debt: ...`), the original criteria plus a residual criterion, the
   original priority/complexity/due date, and a description carrying the
   decision and remaining work. It enters the normal backlog and can be
   triaged, assigned, and executed like any other card.
6. A transient provider, worktree, or environment failure stops the current
   workflow pass after recording the failure. It does not consume the
   remediation budget, so an outage never closes cards with debt.
7. Schema v17 adds `stories.debt_of_story_id` with an index. No state-check
   change, no new table, no dependency, and no provider-contract change.
8. Audit adds the content-free `story_debt_created` event for the follow-up card
   (story identifier only). The original card records `story_completed`; the
   existing remediation and failure events are unchanged.
9. The Tech Lead receives a bounded markdown closure recap memory (ADR-0068)
   that names the decision, the residual work, and the debt card.
10. Tests cover the closing path, the linked unassigned debt card, the absence
    of new `BLOCKED` rows, the strict closure parser and fallback, memory
    creation, and the transient-failure stop.

## Consequences

- Every autonomous card reaches `DONE`; none waits for a human or bounces
  between columns.
- Technical debt becomes visible and traceable instead of hidden in a blocked
  card's history.
- A compromised card records the decision as its review text; reviewers and the
  Kanban show that it was closed by the Tech Lead, not that the work passed a
  normal review.
- Unassigned debt cards stay in `TODO` until someone assigns them, which avoids
  an unbounded chain of automatic follow-ups in one pass.
- The extra closing provider call is bounded by the same timeout and output
  budget as remediation and has a deterministic fallback.

## Alternatives considered

- **Keep `BLOCKED` as a terminal state**: rejected; it stops the autonomous
  flow and was the source of the oscillation.
- **Mark the card `DONE` without a decision**: rejected; it fabricates success.
- **Delete the failed card**: rejected; it hides evidence and loses the work.
- **Create the debt card assigned and in progress**: rejected; it would execute
  immediately and can chain indefinitely.
- **Let the model choose the debt card state or skip the debt**: rejected; the
  application owns the transition and the bounded follow-up.
- **Unbounded remediation or closure attempts**: rejected; budget and deadline
  remain mandatory.
