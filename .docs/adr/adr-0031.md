# ADR-0031: Repository-local data for debug builds

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amends: ADR-0002, ADR-0014 (debug-build fallback only)

## Context

ADR-0002 and ADR-0014 keep installed VLab on per-user directories and use the
repository `.data/` folder only through `make run`, which sets
`VLAB_CONFIG_DIR` and `VLAB_DATA_DIR`. The product owner expects the debug
binary built in this repository to read and write the same `.data/` folder when
invoked directly as `./target/debug/vlab`; running it without the Makefile
currently resolves per-user paths and fails when no per-user settings exist.

The request is a development ergonomics change, not a change to the installed
product. A raw debug binary must not silently use an arbitrary working
directory, because that would make configuration and database selection depend
on where the process was started.

## Decision

1. In **debug builds only**, when none of `VLAB_CONFIG_DIR`, `VLAB_DATA_DIR`,
   or `VLAB_DB_PATH` is set, VLab looks for a `.data/` directory next to the
   repository root inferred from the executable path:
   `<exe-dir>/../..` for the Cargo layout `<repo>/target/debug/vlab`.
2. If that `.data/` directory exists, both the configuration directory and the
   data directory resolve to it; the database is `<repo>/.data/vlab.db`.
3. The fallback never creates `.data/`; it only uses an existing directory and
   only when the executable sits in the expected `target/debug` layout.
4. Explicit path overrides always win. Release builds and installed binaries
   keep the per-user defaults of ADR-0002. The integration-test sandbox still
   sets explicit overrides, so tests remain isolated.
5. The fallback is derived from the executable path, never from the current
   working directory, so starting VLab elsewhere cannot select another
   project's settings or database.
6. `make run` remains supported and explicit; it produces the same `.data/`
   result.

## Consequences

- `./target/debug/vlab --show-settings` in a repository clone uses
  `.data/settings.yaml` without a wrapper or exported variables.
- Moving or copying the debug binary away from the `target/debug` layout
  disables the fallback and returns to per-user paths.
- A release build behaves exactly as before, so packaging and installed use are
  unaffected.
- Debug runs from this repository no longer exercise the per-user default;
  release verification must still cover it.
- A `.data/` directory that happens to exist in a similarly shaped directory
  would be selected; the shape is specific enough for a development checkout,
  and explicit overrides remain available.

## Alternatives considered

- **Use `make run` only**: rejected by the product owner, who wants the direct
  debug binary to work.
- **Change the default for every build**: rejected; it would move installed
  data into the current working directory and contradict ADR-0002.
- **Read the current working directory**: rejected; path selection would
  depend on where the process starts.
- **Symlink the per-user directory to `.data`**: rejected; it is machine-local
  and not reproducible for other contributors.
- **Auto-load a `.env` file**: rejected; it adds a dependency and another
  implicit configuration source.
