# ADR-0071: Bounded rework from review findings and Tech Lead escalation

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0050 (bounded execution), ADR-0069 (closing compromise),
  ADR-0070 (develop integration)

## Context

A rejected review sent the story back to `IN_PROGRESS`, but the workflow
recreated the story branch and worktree from `HEAD` on every attempt. The next
agent therefore lost the previous work, redid the whole story, and frequently
stopped again at the work round limit. The reviewer then rejected the partial
result again. Cards could move `IN_PROGRESS -> IN_REVIEW -> IN_PROGRESS`
several times without converging, and a work-round-limit result was still sent
to review even though it was not a complete submission.

The product owner requires a different flow:

1. A reviewer either accepts the card or returns it with every concrete issue
   and reassigns it to the same assignee.
2. The rework agent fixes only the reported issues and resubmits to review.
3. The reviewer retests only that scope.
4. If the assignee cannot fix it, the Tech Lead must take over, reassign to a
   different agent with more instructions, or close the original card and open
   a new card containing only the remaining changes.
5. The card must not loop.

## Decision

1. **Preserve the story branch and worktree on retry.** A retry reuses the
   existing `vlab/<story-id>` branch and worktree, including the previous
   commits and any uncommitted work, instead of recreating it from `HEAD`.
   A new branch is created only for the first attempt.
2. **Structured review findings.** The reviewer output is strict JSON with
   `review_outcome`, `accepted`, `findings` (1–8 concrete items, each bounded),
   and an optional `retest` scope. A rejection without findings uses the review
   text as the single finding. Accepted reviews may omit findings.
3. **A work-limit result is not a review submission.** When the work loop stops
   at the round or deadline limit, the application records an incomplete
   outcome, does not call the reviewer, and leaves the story `IN_PROGRESS`.
   The next step is a bounded rework, not another `IN_REVIEW` transition.
4. **Bounded failure counter.** Schema v20 adds `stories.rework_attempts` and
   stores `review_findings_json` and `review_retest` on `story_outcomes`.
   `rework_attempts` increments on each review rejection or work-limit failure.
5. **First failure: same assignee rework.** With `rework_attempts = 1`, the
   workflow writes a rework context listing only the reviewer findings and
   retest scope, keeps the same assignee, resets execution attempts, clears the
   rejected outcome, and leaves the story in progress. No Tech Lead call is
   needed.
6. **Second failure: Tech Lead escalation.** With `rework_attempts = 2`, the
   Tech Lead receives the original story, the findings, the previous review,
   and the roster, and must choose a different active agent with additional
   instructions. The application rejects the previous assignee when another
   candidate exists; if no other agent exists, it closes with debt. The context
   is stored as untrusted prompt data.
7. **Third failure: close with debt.** With `rework_attempts >= 3`, or after
   three remediation cycles, the Tech Lead records a closing compromise, the
   original card becomes `DONE`, and one unassigned `TODO` technical-debt card
   contains the remaining findings. This is the hard stop; no further automatic
   rework occurs.
8. **Review scope.** The follow-up reviewer receives the previous context and
   findings and is instructed to verify only those items and regressions from
   the latest diff. It still reviews the latest commit, which contains only the
   fix because the branch is preserved.
9. **Unavailable or invalid review output.** It is not accepted. A synthetic
   rejection with one actionable finding is recorded and the bounded
   remediation path handles it. A card is never marked `DONE` without a valid
   review.
10. **Events.** A content-free `story_reworked` event distinguishes a direct
    same-assignee rework from `story_remediated` (Tech Lead escalation) and
    `story_completed` / `story_debt_created` (closure). No review text,
    findings, diffs, or git output enter audit events.

## Consequences

- Rework converges because the previous work is preserved and the scope is the
  reviewer's findings, not the whole story.
- Work-limit failures no longer churn through `IN_REVIEW`; they become a
  bounded rework or escalation.
- A card reaches `DONE` at the latest after three failed attempts, with the
  residual work visible as a debt card.
- The review output and outcome row carry a small structured findings list;
  this is project data, bounded and rendered sanitized.
- A reviewer outage produces a synthetic rejection and can consume a bounded
  remediation cycle; it never fabricates `DONE`.

## Alternatives considered

- **Recreate the worktree on every retry**: rejected; it destroys the work the
  rework is supposed to fix and causes the observed loop.
- **Keep the 3 remediation cycles without a direct rework**: rejected; every
  rejection would call the Tech Lead and the developer would still restart.
- **Send work-limit results to review**: rejected; the reviewer correctly
  rejects them, creating a needless `IN_REVIEW` cycle.
- **Unbounded rework**: rejected; three failures is the hard bound.
- **Let the model choose the loop policy**: rejected; the application owns the
  counters and transitions.
- **Open a new card on every rejection**: rejected; it fragments the same work.
