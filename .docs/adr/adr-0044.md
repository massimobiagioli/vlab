# ADR-0044: Request intake from the dashboards

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0038 (Projects dashboard actions), ADR-0043 (Kanban keymap)

## Context

ADR-0039 made the dashboards the only public entry point; `--new-request`
remains a hidden legacy flag. The Kanban empty state still told users to run
`vlab --new-request`, which they can no longer discover. The product owner
asked for a Projects action that opens a simple, clean prompt dialog to submit
a request.

Planning calls the provider, can take up to the 240-second deadline, and must
keep every existing bound: one database connection, no retry after
cancellation, the request row written before the call, and no content in logs
(ADR-0026, SECURITY.md).

## Decision

1. **Entry points.** The Projects dashboard gains `r` (Request) for the
   selected project. The Kanban screen gains `n` (New request) for the shown
   project. Both make the project current (ADR-0033) and open the same dialog.
   The Kanban empty state says `Press n to submit a request.`
2. **Prompt dialog.** A centered dialog titled with the project name holds one
   bordered, accent-colored text area with a visible cursor and word
   wrapping (a word longer than a row is split). It scrolls to keep the cursor visible. Keys: typing
   inserts, `Backspace`/`Delete`/`←`/`→`/`Home`/`End` edit, `Alt+Enter` inserts
   a line break, `Enter` submits, `Esc` cancels. A muted footer shows the keys
   (shortened on narrow terminals) and the character count. Bracketed paste is enabled while the dashboard
   runs; pasted text keeps line breaks (`\r\n` → `\n`) and drops other control
   characters. An empty or whitespace-only request is not submitted.
3. **Same use case.** Submission calls `app::requests::plan` with the default
   `ExecutionLimits`, the provider built from `settings.yaml` exactly as the
   flag path does, and the dashboard run identifier. Size, credential, and
   laboratory checks stay in the use case.
4. **Execution.** Planning runs on the main thread with the dashboard's single
   database connection. A `Planning…` dialog is drawn first. A helper thread
   only reads terminal events; `Esc` or `Ctrl-C` cancels the token, and the use
   case discards any late response (no retry). The helper stops and is joined
   before the dashboard reads input again.
5. **Outcome.** A dialog reports the result: planned stories (title and
   assignee), clarification questions, the failure code and hint, or
   cancellation with the provider-side warning. All model text is sanitized.
   Errors raised before the request row exists use the existing error dialog.
   The Projects table and an open Kanban board reload afterwards.

## Consequences

- Request intake is discoverable without legacy flags; the hint no longer
  points to a hidden command.
- The terminal stays in the dashboard during planning; no extra database
  connection or provider path is introduced.
- The dashboard cannot redraw an animation while the provider call blocks; the
  `Planning…` dialog is static.
- Kanban reload remains `r`; on the Projects dashboard `r` means Request.

## Alternatives considered

- **Restore the terminal and print CLI output** (like the agent wizard):
  rejected; it leaves the dashboard for a single prompt.
- **Planning on a worker thread with its own connection**: rejected; it breaks
  the single-connection rule for an animation.
- **Single-line form field**: rejected; requests are often several sentences
  or pasted text.
- **`n` on Projects**: taken by New project.
