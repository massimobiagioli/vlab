# ADR-0028: Content-free interaction metadata (schema v5)

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

Planning and direct questions need diagnostics for provider behavior, retries,
latency, and token use without retaining prompts, answers, request text,
memories, CVs, or provider payloads. `SECURITY.md` and `data-retention.md`
require minimization and forbid secrets/content in durable operational data.
WP-6 introduces interaction metadata shared by both workflows.

## Decision

1. Add schema v5 `interactions` with `id`, `run_id`, `agent_id`, `kind`
   (`planning`/`question`), `provider`, `model`, `outcome`
   (`success`/`failure`/`cancelled`), `error_code`, `duration_ms`,
   `input_tokens`, `output_tokens`, and `created_at`.
2. Store no content columns. Questions, answers, prompts, request text,
   memories, CVs, and provider bodies are never persisted here.
3. Record exactly one interaction per logical invocation, including failure and
   cancellation. The shared invocation service records it after the retry
   policy returns.
4. Keep the agent identifier and run identifier for correlation; no user text
   is accepted by the API.
5. Index agent and creation time for diagnostics and cleanup planning.
6. Interactions are operational metadata, not project data. They are retained
   for troubleshooting and evaluation; there is no automatic purge in the
   initial release. Deleting a laboratory/project does not delete unrelated
   interaction rows.

## Consequences

- Operators can inspect model/provider/outcome/latency/token metadata without
  exposing user content.
- The table grows with invocations; no automatic cleanup exists and this is
  documented as a limitation.
- The interaction schema is shared by planning and questions, avoiding two
  divergent metadata paths.
- An interaction row can exist for an operation whose request was later
  deleted; it contains identifiers only and no content.

## Alternatives considered

- **Log-only metadata**: rejected; structured local records survive diagnostics
  being off and are easier to test.
- **Store prompts/responses for debugging**: rejected by `SECURITY.md` and
  data-minimization rules.
- **Store tokens/cost only in events**: rejected; a dedicated interaction row
  keeps planning/question metadata consistent and supports per-kind queries.
- **Delete interactions with the request**: rejected; they are operational
  records, not project content, and deletion would lose failure evidence.
