# ADR-0015: Strict settings file and atomic in-place editing

- Status: Superseded
- Date: 2026-11-12
- Supersedes: —
- Superseded by: ADR-0030

## Context

Specification §5 fixes `settings.yaml` as the user-editable configuration
file, with exactly `provider` and `model`, and requires that invalid edits
never replace a valid file. It also requires that the editor be launched
without evaluating a shell command string, and that credentials never appear
in the file, output, or errors. `STACK.md` requires concise dependencies and
`SECURITY.md` treats the file and its directory as private storage. WP-2-T3 to
WP-2-T5 implement this behavior; the YAML parser itself is chosen in
[ADR-0008](adr-0008.md).

## Decision

1. **Location and privacy.** `settings.yaml` lives in the per-user
   configuration directory. The directory is created with mode `0700` and
   verified closed to other users; the file is written with mode `0600`
   ([ADR-0010](adr-0010.md)).
2. **Strict schema.** Parsing accepts at most 64 KiB of UTF-8 and exactly two
   text fields, `provider` and `model`, with unknown fields, duplicate keys,
   multiple documents, and non-scalar values rejected. `provider` is
   `deepseek` only. `model` is trimmed to 1–64 characters of
   `[A-Za-z0-9._:-]`; whether the provider accepts it is checked only when a
   provider-backed command runs.
3. **Content-free errors.** A failure is explained from typed parser
   information only: unknown field, missing field, wrong value type, invalid
   YAML, multiple documents, unsupported provider, or invalid model. Messages
   never repeat field values, because a misplaced credential may be one. The
   parser is a pure function over bytes; only the file adapter performs I/O.
4. **Credentials.** The API key is read only from `DEEPSEEK_API_KEY`, and only
   its presence is exposed (`set`/`unset`). The value is never read by settings
   code, stored, or rendered.
5. **Atomic edit.** `--edit-settings` resolves `VISUAL`, then `EDITOR`, splits
   it into executable and arguments with `shell-words`, and runs the program
   directly with no shell and no `eval`. A new file starts from a commented
   template whose placeholder model is invalid. The working copy is a private
   `0600` file in the same directory; on success it is flushed, renamed over
   the original, and the directory is flushed. On any failure the draft is
   deleted and the previous bytes are preserved. Stale drafts from interrupted
   edits are removed before a new one is created.
6. **No side effects.** `--show-settings` and `--edit-settings` make no
   provider call, open no database, and create no file other than the settings
   file (or its private draft while editing).
7. **Layering.** The typed model and validation rules live in
   `src/domain/settings.rs`; the file adapter and error reasons live in
   `src/infra/config.rs`; the use cases and ports live in
   `src/app/settings.rs` and `src/app/settings_edit.rs`; the editor process
   lives in `src/cli/prompt.rs`.

## Consequences

- The user can always recover by running `--edit-settings`; no partial or
  invalid file replaces a valid one.
- A misplaced key in the file is reported by field name and does not leak.
- The file format is deliberately small; adding a field requires an ADR, a
  schema update, and tests.
- `shell-words` parsing is documented and tested with a path containing a
  space; an editor value with unbalanced quotes is a configuration error.
- Existing settings directories that grant group or other access are refused
  rather than repaired, matching the fail-closed rule of ADR-0010.

## Alternatives considered

- **Loose YAML parsing with defaults**: rejected; a typo would silently select
  a wrong model or be ignored, and unknown fields could hide a misplaced
  credential.
- **Editing the file in place**: rejected; an editor crash or invalid save
  would destroy the working configuration.
- **Launching the editor through `sh -c`**: rejected; it is unnecessary shell
  evaluation and a command-injection surface.
- **Storing credentials in the file**: rejected by specification §5.1 and
  `SECURITY.md`.
- **Detecting credential-looking values and redacting them**: rejected as a
  heuristic; strict field rules and value-free messages are simpler and
  stronger.
