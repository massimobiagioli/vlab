# ADR-0043: Project editing and full-screen Kanban board

## Context

The Projects dashboard can create, open, assign, and delete projects, but a
project name cannot be corrected after creation. The Kanban action (`v`) opens
the board as a text dialog over the project table; the product owner found it
unsuitable and asked for a dedicated screen that behaves like a card board
(Trello-style lists of cards) while keeping the existing visual language.

The specification keeps the board read-only: the initial release creates only
`TODO` stories and the board must not imply that execution or state transitions
exist (TECHNICAL-SPECIFICATIONS §10).

## Decision

1. **Project edit.** The Projects dashboard gains `e` (Edit). It opens the
   ADR-0042 form with one field, Name, prefilled with the selected project.
   `app::projects::rename` requires an active laboratory, verifies that the
   project belongs to it, validates the name with the existing name rule, and
   updates `projects.name` and `projects.updated_at`. No schema change.
2. **GitHub source is immutable.** The source is not editable: it names the
   checkout already cloned into `.workspace/<project-id>` (ADR-0032), and
   changing it would require a re-clone, credential use, and checkout removal.
   A different repository needs a new project.
3. **Audit.** A successful rename records a typed `project_updated` event with
   the project identifier only.
4. **Kanban screen.** `v` opens the selected project's board as its own
   full-screen dashboard screen, not a modal. It keeps the dashboard frame:
   header block with project, laboratory, Tech Lead, optional GitHub source,
   story counts, and pending intake; a body; and the persistent Actions bar.
5. **Board layout.** The body renders the five states as side-by-side bordered
   lists titled with the state label and count. A card shows only the story's
   short description (its title), word-wrapped to at most three lines and
   ending with `…` when cut; the card height follows the text. Identifier,
   assignee, priority, dates, and warnings are not on the card. The focused
   list and the selected card use the accent border; the selected card also
   uses the selection style, so focus never relies on color. When the terminal
   cannot fit five lists at a readable width, a window of adjacent lists
   containing the focused one is shown with `‹`/`›` indicators.
6. **Per-list scrolling.** Every list keeps its own selected card and scroll
   offset; changing list never resets another list. The offset moves by the
   minimum needed to keep the selected card fully visible, computed from the
   real card heights at render time, and shrinks again after a resize. The
   list border shows `↑N` (cards above), `↓N more` (cards below), and
   `position/total` when not every card fits.
7. **Board keys.** `←/→` or `h/l` move between lists; `↑/↓` or `j/k` move
   between cards and scroll at the edges; `PgUp/PgDn` move by one visible page;
   `Home/End` or `g/G` jump to the first/last card; `Enter` opens the card
   detail; `r` reloads; `?` shows help; `Esc` returns to the Projects dashboard
   with its selection; `q` quits.
8. **Card detail dialog.** `Enter` opens a dialog over the board with every
   story field: title, state, assignee or `Unassigned`, priority, complexity,
   due date with an `! OVERDUE` marker, required skills, originating request,
   story identifier, description, acceptance criteria, and assignment
   rationale. Labels are aligned and text is word-wrapped. Long content scrolls
   with `↑/↓`, `PgUp/PgDn`, `Home/End`, with a `position/total` hint; `Esc` or
   `Enter` closes it. The data is read through `app::kanban::story`, which
   scopes the story to the project and the active laboratory. All text is
   sanitized before rendering.
9. **Read-only.** The board never changes story state. Moving cards between
   lists is out of scope until a specification change introduces state
   transitions.

## Consequences

- Projects can be renamed without recreating them; checkouts stay consistent.
- The Kanban gains navigation and detail without new provider calls or writes.
- The board stays legible at 60×20 by showing fewer lists at a time.
- Cards are compact and scannable; details cost one key press.
- A future state-transition feature can add move keys to the same screen.

## Alternatives considered

- **Keep the Kanban dialog**: rejected by the product owner.
- **Vertically stacked sections in the TUI**: rejected; it does not read as a
  board. Stacked output remains the plain `--show-project-kanban` fallback.
- **Editable GitHub source**: rejected; see decision 2.
- **Fields on the card** (identifier, assignee, priority, due date): rejected
  by the product owner; the card shows the short description only.
- **Fixed-height cards**: rejected; short titles wasted rows and reduced the
  number of visible cards.
- **Move cards between lists now**: rejected; contradicts the read-only board
  in the specification.
