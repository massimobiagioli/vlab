# ADR-0046: Manual laboratory and project memories from the floor

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0022 (content editing), ADR-0035 (manual surface),
  ADR-0036 (manual surface)

## Context

ADR-0035 removed the manual memory commands and ADR-0036 made memories
application-managed: structural events and planning summaries write them, and
no user command lists, creates, or deletes them. The product owner now wants to
manage laboratory and project memories from the new laboratory floor: create a
laboratory memory, create a project memory, view both scopes, edit either, and
delete either.

This restores a small manual surface, not the old CLI flags. It must preserve
the existing trust model: memory text is untrusted prompt context, the provider
credential is rejected, scopes are bound to the active laboratory and its
current project, per-scope capacity is enforced, and no model or provider call
happens while editing. Agent memories stay application-managed.

## Decision

1. **Entry and scope.** The floor action `m` opens a full-screen `Memories`
   screen with two tabs, `Lab` and `Project`. The laboratory tab uses the active
   laboratory; the project tab uses the current project. With no current
   project, the project tab is read-only and explains how to open one. The
   screen is interactive-only; no CLI flag is added.
2. **Operations.** The screen lists memories newest first and supports:
   create (`n`), view (`Enter`), edit (`e`), and delete (`d`). Editing replaces
   the content only; the identifier, scope, and creation timestamp are
   unchanged. A create is refused when the scope already holds 20 memories.
3. **Validation.** Content is trimmed, must be 1–2,000 characters, and may
   contain newlines and tabs but no other control characters. Content
   containing the configured DeepSeek credential is rejected before the write.
   The editor is multiline (`Alt+Enter` inserts a line break); `Enter` saves and
   `Esc` cancels. Validation and storage errors stay in the editor as a notice.
4. **Ownership.** A laboratory memory is valid only for the active laboratory.
   A project memory is valid only for the current project in that laboratory.
   A memory identifier from another scope or laboratory is not found. Agent
   memories are never listed or changed from this screen.
5. **Deletion.** `d` opens the existing bound confirmation with the exact
   memory identifier, scope, and a short preview. `y` deletes; `n` or `Esc`
   cancels. The confirmation is the same one used by other destructive
   dashboard actions; there is no non-interactive path.
6. **Observability and security.** Manual creates, edits, and deletes record
   `memory_created`, `memory_updated`, and `memory_deleted` with only the memory
   identifier; content is never logged or stored in events. The new
   `memory_updated` event kind is added to the typed event set. All displayed
   content is sanitized. No provider call, model output, CV, or credential is
   rendered.
7. **Persistence.** The existing `memories` table is used unchanged. The
   repository gains an update statement for content by identifier. No
   migration is required.

## Consequences

- Users can inspect and correct the prompt context that planning uses, and can
  free capacity in a full scope.
- Manual content is now user-authored again and must be treated as untrusted
  prompt input; the existing credential and scope checks still apply.
- ADR-0036 remains in force for automatic generation; only its statement that
  no user surface exists is amended.
- The floor gains a second screen and the TUI gains a multiline memory editor
  and detail dialog. Storage, provider, and retention behavior are otherwise
  unchanged.

## Alternatives considered

- **Restore the old CLI flags**: rejected; the product owner wants the actions
  from the floor, and a second surface would duplicate validation and
  authorization.
- **Read-only memories**: rejected; editing and deletion are explicitly
  required.
- **Edit by delete and recreate**: rejected; it loses the identifier, creation
  time, and audit continuity.
- **Allow agent memories too**: rejected; agent memories remain part of the
  automatic lifecycle and are not requested here.
- **Add an `updated_at` column**: rejected; edits preserve creation time and
  the existing schema is sufficient.
- **Use the model to rewrite memories**: rejected; model output is not
  authority and would add a new trust boundary.
