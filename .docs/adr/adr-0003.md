# ADR-0003: Bounded DeepSeek integration with no agent tools

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amended by: ADR-0030 (credential source only)
- Amended by: ADR-0048 (bounded no-tool workflow simulation)
- Amended by: ADR-0050 (bounded real execution with tools)

## Context

The product uses a remote model to produce structured proposals and answers.
Model output is untrusted: it may be malformed, adversarial, or wrong, and it
must never grant permissions, execute code, or determine that an external
effect occurred. Outbound requests leave the application's trust boundary and
may incur cost. `ARCHITECTURE.md` and `SECURITY.md` require bounded execution,
explicit failure classification, minimal data transmission, and authorization
outside the model.

## Decision

1. Define a narrow `ModelProvider` port in the domain/application boundary and
   implement a DeepSeek adapter in infrastructure using `reqwest` with rustls.
   Keep TLS certificate validation enabled.
2. Support one provider (`deepseek`) in the initial release. Read the API key
   only from `DEEPSEEK_API_KEY`; never accept it as a command-line argument,
   store it in the database, or write it to logs.
3. Expose **no tools** to the model. There is no filesystem, shell, network, or
   code-execution capability. The provider connection is application
   infrastructure, not an agent capability. **Amended by ADR-0050:** the
   execution workflow now exposes four validated worktree tools; the planning
   and question paths still expose none.
4. Use one logical planning invocation per accepted request, with at most two
   retries for retryable transport, rate-limit, and server failures. Use
   exponential backoff with jitter and a per-attempt timeout of 60 seconds.
   Never retry authentication failures, invalid output, cancellation, or
   oversized responses.
5. Enforce explicit limits: request size, response size, story count, output
   tokens, and a total deadline. Validate limits before dispatch and while
   reading the response. Stop dispatching after cancellation or budget
   exhaustion.
6. Require structured JSON output for planning, parsed with strict schema
   validation. Reject unknown fields, unknown identifiers, missing fields, and
   invalid enumerations. Do not attempt an automatic repair loop.
7. Perform all validation, assignment checks, date calculation, persistence,
   and authorization locally in application code.
8. Send only the context required for the operation. Do not transmit CV
   content, unrelated projects, chat transcripts, or secrets.
9. Record provider/model identifiers and minimal outcome metadata for
   troubleshooting; never record prompts or response bodies by default.

## Consequences

### Positive

- The blast radius of prompt injection is bounded: the model can only produce
  data that local validation may reject.
- Provider coupling is isolated behind one adapter and a deterministic test
  double.
- Cost and latency are bounded and observable.

### Negative / trade-offs

- No tool-using agent capabilities; the product is intentionally less
  autonomous.
- Retries may incur additional provider charges, and exactly-once remote
  execution cannot be promised.
- Structured output can fail more often than free-form text; failures must be
  reported rather than hidden.

## Alternatives considered

- **Agent framework with tools**: rejected by the architecture and security
  baselines for the initial scope.
- **Multiple providers initially**: rejected as unnecessary complexity; add
  through a new ADR when required.
- **Streaming responses**: deferred; non-streaming simplifies size limits and
  cancellation.
- **Automatic output repair**: rejected because it can loop, increase cost, and
  blur the boundary between proposal and validated data.
