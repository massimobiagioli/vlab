# ADR-0002: Local SQLite persistence and per-user configuration storage

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amended by: ADR-0030 (credential source only)
- Amended by: ADR-0031 (debug-build path fallback only)

## Context

The application needs durable local state for domain entities and execution
metadata, plus user-editable provider settings. It must work without an
external database service, keep sensitive data private, and remain recoverable
after partial failures. `STACK.md` mandates SQLite through SQLx, a single
connection initially, foreign-key enforcement, versioned migrations, and
private per-user storage locations. `SECURITY.md` requires minimizing stored
sensitive data and keeping credentials out of storage.

## Decision

1. **Settings**: store `settings.yaml` in the operating system's per-user
   configuration directory. It contains only `provider` and `model`. It never
   contains credentials. Resolve the API key from `DEEPSEEK_API_KEY`.
2. **Application state**: store the active laboratory selection in the SQLite
   `app_state` table, not in `settings.yaml`.
3. **Database**: use one SQLite database in the operating system's per-user
   application-data directory through SQLx.
4. **Connections**: begin with a single connection (`max_connections = 1`).
   Enable and verify `PRAGMA foreign_keys = ON` for every connection. Set a
   bounded `busy_timeout` (5 seconds). Keep WAL disabled until measured
   concurrency requires it and the filesystem supports its locking semantics.
5. **Schema changes**: use embedded, forward-only, versioned migrations named
   `NNNN_description.sql`. Never edit an applied migration. Refuse to open a
   database whose schema is newer than the binary supports.
6. **Queries**: use parameterized statements only. Keep transactions short and
   make multi-entity writes atomic. Prefer runtime-checked queries in tests
   over build-time database coupling.
7. **Permissions**: create directories with mode `0700` and files with mode
   `0600` on Unix. Fail closed if private storage cannot be established.
8. **Data minimization**: do not store provider credentials, prompts, provider
   response bodies, or full chat transcripts. Retain only domain data and
   minimal execution metadata.
9. **Overrides**: allow `VLAB_CONFIG_DIR`, `VLAB_DATA_DIR`, and `VLAB_DB_PATH`
   for tests and controlled deployments.

## Consequences

### Positive

- No external service to install or operate.
- Transactions give atomic domain updates and predictable recovery.
- Per-user paths and permissions reduce accidental disclosure.
- Migrations are reproducible and testable.

### Negative / trade-offs

- SQLite is a single-writer database; concurrent CLI processes may contend.
- WAL is not used, so read/write concurrency is limited.
- Data at rest is not encrypted by SQLite; the application must document this
  and rely on operating-system storage protection.
- Embedded migrations increase binary size slightly.

## Alternatives considered

- **JSON files per entity**: rejected because atomic multi-entity updates,
  referential integrity, and querying would be fragile.
- **PostgreSQL or another server**: rejected by `STACK.md`; unnecessary
  operational burden for a local CLI.
- **WAL immediately**: deferred because there is no demonstrated concurrency
  requirement and WAL is unsafe on some network filesystems.
- **Credentials in the database**: rejected; environment-based injection is
  simpler to protect and rotate.
