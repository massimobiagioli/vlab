# ADR-0068: Markdown recap memories for planning and completed cards

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0022 (scoped memories), ADR-0036 (automatic memories), ADR-0059
  (markdown file store)

## Context

Automatic project memories were written as raw snippets such as
`Planning summary: ...`. The file store made them markdown files, but the
content did not read as a recap: it had no title, request, story list, or
metadata. Agents also had no automatic memory of the cards they completed, so
an agent profile did not accumulate a useful work history.

The product owner expects the project memory folder to contain real markdown
recaps and expects agents to gain a memory when they close a card.

## Decision

1. After a successful plan, write one project-scope markdown recap with a
   bounded title, date, project, request identifier, original request, story
   list (title, assignee, state, due date), and the optional Tech Lead summary.
2. After an accepted review, write one agent-scope markdown recap for the
   assignee with the card identifier, project, story, branch, commit, work
   summary, review outcome, and Tech Lead context when present.
3. Both recaps are built deterministically from stored data and the existing
   bounded model summary. They are trimmed to the memory limit (2,000
   characters) and written through the existing memory/file-store path; a full
   scope remains best effort and never fails the triggering action.
4. Recap content is untrusted project data, sanitized for display, never
   executed, and subject to the same credential rejection rules.
5. Existing raw automatic memory files remain readable. A local backfill may
   wrap them as markdown without changing identifiers; the application does not
   rewrite user-authored memories automatically.
6. No schema, dependency, provider-contract, or retention change.

## Consequences

- Project memory files are readable recaps rather than raw model snippets.
- Agents accumulate a bounded card-completion history; the 20-memory cap still
  applies and old memories must be managed as before.
- Planning creates a project recap even when the optional model summary is
  unavailable.
- Memory prompts receive the same bounded text as before, now with markdown
  headings that are still delimited data.

## Alternatives considered

- **Keep one-line summaries**: rejected; they are not useful recaps.
- **Store recaps in a new table**: rejected; the file store already holds memory
  markdown and SQLite must keep only references.
- **Generate recaps with an additional model call**: rejected; the data is
  already available and deterministic composition is cheaper and safer.
- **Rewrite all historical memories automatically**: rejected; it would mutate
  user-authored content without consent.
