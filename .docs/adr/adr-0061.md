# ADR-0061: Background request queue with serial Tech Lead processing

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0049 (startup resume), ADR-0023 (request lifecycle), ADR-0050
  (bounded execution)

## Context

Today a request is planned inside the action that submits it. The dashboard
shows a blocking `Planning…` dialog, runs the provider call and the bounded
workflow on the UI thread, and only then accepts another request. The request
row is briefly `TODO`, then `PLANNING`, but the operator cannot submit a second
request until the first one finishes.

The product owner wants intake to be immediate: the request must appear in the
`TODO` column at once, and a Tech Lead must drain the queue in the background,
one request at a time. The second request waits in `TODO`; it does not block the
dashboard. This must not become an autonomous daemon or unbounded parallel
execution.

## Decision

1. **Enqueue only.** Dashboard submission and `--new-request` validate the text
   and persist one request row with status `TODO`. They call no provider and run
   no workflow. The operator receives the request identifier immediately.
   Enqueueing records one content-free `request_queued` event.
2. **One serial worker.** While the interactive application runs, one bounded
   in-process worker drains queued requests for the active laboratory, oldest
   first. It runs the existing planning state machine and the existing bounded
   worktree workflow (ADR-0050) for one request before selecting the next. There
   is no parallel provider call, no thread per request, and no model-chosen
   queue order.
3. **Separate connection, no terminal access.** The worker opens its own SQLite
   connection and never draws, reads keys, or holds the terminal. The dashboard
   keeps its own connection and refreshes on worker events. SQLite's busy
   timeout serializes short writes; no transaction spans a provider call.
4. **Bounded headless drain.** Hidden `--run-queue` (and `make run-queue`)
   processes at most eight queued requests for the active laboratory, then
   exits. `--new-request` itself never waits for planning. The interactive
   worker keeps the existing 240-second planning lease and stale-`PLANNING`
   recovery: a request abandoned by a crash becomes `FAILED` with
   `stale_planning`; it is not retried automatically.
5. **Failure isolation.** A failed, cancelled, or clarification outcome is
   persisted on that request and the worker moves to the next request. A
   missing provider configuration leaves the request in `TODO` and the worker
   backs off instead of spinning or losing it. Workflow failures keep the
   existing retry and `BLOCKED` behavior; startup resume remains as amended from
   ADR-0049.
6. **Kanban visibility.** The `TODO` column renders queued requests as
   `REQUEST` cards before stories. `TODO` means waiting; `PLANNING` means the
   Tech Lead has picked it up. The card shows the sanitized request text, and
   `Enter` opens a read-only request detail. When planning completes, the
   request card disappears and its stories appear through the normal board
   refresh.
7. **Shutdown.** Quitting the dashboard stops selecting new requests and
   cancels the shared cancellation token. The process may exit while an
   in-flight provider call unwinds; no background process survives the
   application.
8. **No new schema.** The queue is the existing `requests.status = 'TODO'`
   state. No table, column, migration, dependency, or provider contract changes.
   Events stay content-free.

## Consequences

- Intake is immediate and two consecutive requests are accepted without
  waiting; the second remains visible in `TODO` until the first finishes.
- Provider and workflow work happens while the dashboard remains usable, but
  only one request is processed at a time and only while VLab is running.
- The UI must tolerate concurrent reads while the worker writes and must refresh
  on completion; short SQLite lock waits are possible.
- `--new-request` no longer prints planned stories. Scripts must run
  `--run-queue` (or start the dashboard) to process the queue.
- The worker uses the active laboratory. Queued requests in another laboratory
  wait until that laboratory becomes active.
- Queue progress is durable in `requests`; no request is lost on navigation.

## Alternatives considered

- **Keep synchronous planning**: rejected; it blocks the dashboard and prevents
  the second request, contrary to the product requirement.
- **A background daemon or OS service**: rejected; VLab is a local one-shot CLI,
  and a daemon adds lifecycle, security, and operations surface.
- **One thread per request**: rejected; it creates parallel model calls and
  unbounded cost, with no benefit for a single Tech Lead.
- **A new queue table/status**: rejected; `requests` already has `TODO` and the
  ordering fields needed. A schema change would add retention and migration
  cost without new behavior.
- **Model-chosen prioritization**: rejected; the oldest request is deterministic
  and the model has no authority over ordering.
- **Headless auto-spawn after `--new-request`**: rejected; it would recreate the
  synchronous wait the feature removes.
