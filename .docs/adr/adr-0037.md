# ADR-0037: Tracked feature plans with task checklists

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0007 (tracked planning scope only)

## Context

The implementation plan sequences the initial release, but later product
features need their own durable plan. The product owner requires:
`.project/features/` to be tracked; each feature file named
`nnnnn-feat-<short-description>.md`; the short description to identify the
branch; the plan to be a task checklist; and the feature to be closed only when
every task is checked. ADR-0007 tracked only
`.project/IMPLEMENTATION-PLAN.md` and excluded the rest of `.project/` from
version control.

Feature plans are delivery artifacts, not product specification. They must not
silently override `.docs/` or accepted ADRs.

## Decision

1. **Location and tracking.** `.project/features/` and every
   `*.md` file directly inside it are tracked. Other `.project/` content
   remains local scratch and stays ignored. The implementation plan remains
   tracked as before.
2. **Naming.** A feature file is
   `nnnnn-feat-<short-description>.md`, where `nnnnn` is a zero-padded
   five-digit sequence and `<short-description>` is lowercase kebab-case ASCII.
   Numbers are allocated once, never reused, and the next number follows the
   highest existing file. The short description identifies the feature branch;
   the branch is `feat/<short-description>`.
3. **Required content.** Every feature plan states the identifier, title,
   branch, status, date, related ADRs, goal, non-goals, acceptance criteria,
   risks, and an ordered checklist of tasks. Each task is a Markdown checkbox
   and must have an observable deliverable. Design decisions that change the
   command surface, dependencies, security controls, data model, or tracked
   layout must be recorded as ADRs before implementation.
4. **Checklist discipline.** The checklist is the delivery state. A task is
   checked only when its deliverable and verification exist. The feature is
   complete only when every task is checked, `make check` passes, hosted CI is
   green, and the documentation and ADRs are updated. An incomplete feature
   plan may be committed as `Draft` or `In progress`; it must not be marked
   `Done`.
5. **Precedence.** Feature plans rank below the implementation plan and below
   all `.docs/` and ADR content. A conflict is resolved by the precedence in
   `AGENTS.md`, not by editing a feature plan into a new rule.
6. **Status.** A feature plan uses `Draft`, `In progress`, `Blocked`, or
   `Done`. Status changes are part of the feature branch, not a separate
   governance change.
7. **Governance.** `AGENTS.md` documents the convention, the repository layout,
   and the completion rule. `make` and CI remain unaffected by feature plans.

## Consequences

- Feature work is discoverable in the repository and survives tool or machine
  changes.
- A reviewer can see exactly which tasks remain before a feature is closed.
- The checklist can become stale if tasks are edited without evidence; the
  completion rule makes verification part of the task.
- `.project/features/` can grow over time; numbering and status keep it
  navigable.
- Local scratch under `.project/` stays ignored, avoiding accidental commits of
  notes or generated data.

## Alternatives considered

- **Only GitHub issues/projects**: rejected by the product owner; the plan must
  be tracked with the code.
- **One ever-growing implementation plan**: rejected; later features would
  obscure the initial-release sequence and ownership.
- **Free-form feature notes without checklists**: rejected; completion would be
  ambiguous.
- **Track all of `.project/`**: rejected; it would include local scratch.
- **Four-digit or date-based numbering**: rejected; five digits match the
  requested pattern and sort naturally.
