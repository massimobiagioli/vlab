# ADR-0052: Preset agent catalog loaded from a tracked YAML file

- Status: Accepted
- Date: 2026-11-16
- Supersedes: —
- Superseded by: —
- Amends: ADR-0009 (hidden legacy flags), ADR-0020 (agent validation)

## Context

The product owner wants a ready-to-use roster of ten fictional agents with
distinct profiles, roles, and skills, inspired by the names of German, Dutch,
and English footballers of the 1970s and 1980s. The roster must be tracked in
the repository, and a developer command must load it into the local database.
Reproducing the roster by hand through `--new-agent` is slow and error-prone.

The existing agent model supports four roles (`lead`, `dev`, `analyst`, `qa`),
typed descriptions, skill tags, and an optional CV. The wizard validates every
field. The schema allows a profile without laboratory memberships: membership
is a separate many-to-many relation. The YAML parser dependency
(`serde-saphyr`) already exists; no new dependency is needed.

The repository is dashboard-first (ADR-0039) and keeps hidden legacy flags for
scripts (ADR-0009). The Makefile is the supported developer task runner
(ADR-0014). A separate decision, ADR-0053, adds the laboratory screen that
assigns available profiles to a laboratory.

## Decision

1. **Tracked catalog.** `assets/agents.yaml` holds the roster: a versioned
   (`version: 1`), bounded list of agent profiles. The file is limited to
   512 KiB and at most 20 agents, rejects unknown fields, and uses the existing
   domain limits: 1–100 character names, 1–2000 character single-line
   descriptions, 1–32 character lowercase skill tags, and an optional CV under
   64 KiB.
2. **Same validation as the wizard.** Every agent is validated with the domain
   types (`Name`, `Role`, `Description`, `SkillTag`, CV bounds). The roster must
   contain exactly one `lead`; every `dev`, `analyst`, and `qa` must have at
   least one skill (ADR-0020). Duplicate names within the roster are rejected.
3. **Catalog, not membership.** The loader creates agent profiles only. It
   creates no laboratory and writes no membership. A loaded profile becomes
   available to every laboratory through the populate screen (ADR-0053).
4. **New hidden action.** `vlab --load-preset <file>` is a hidden flag in the
   single-action group, like the other migration-window flags. It reads and
   validates the whole file before opening the database, so a malformed roster
   creates no database. It never calls the provider.
5. **Idempotent by name.** A profile whose name matches an existing profile
   case-insensitively is skipped, including an archived profile. A second run
   therefore creates no duplicates. The loader reports created and skipped
   names without changing existing profiles.
6. **Atomic catalog insert.** A new `Directory::insert_agents` port method
   inserts all new profiles in one transaction; the SQLite adapter overrides
   the default loop. A storage failure writes no profile from the run.
7. **Provider and model copies.** Preset profiles copy the provider and model
   from the current settings at load time, as every created agent does
   (specification §5.4).
8. **Developer command.** `make load-preset` builds the debug binary, creates
   the private `.data/` directory, and loads `assets/agents.yaml` with
   `VLAB_CONFIG_DIR` and `VLAB_DATA_DIR` pointing at `.data/` (ADR-0014,
   ADR-0031). The target is listed in `make help` and the README.
9. **Audit and memories.** The dispatch path records one audit event per
   created agent and writes the automatic structural memory for each profile
   with no laboratory. The loader itself performs no provider or terminal I/O.

## Consequences

- A fresh checkout can populate a reusable agent catalog with one command.
- The roster is data, not code: editing it needs no Rust change, but the
  schema is strict and the file is reviewed like documentation.
- The command is non-interactive, so it is safe in scripts and CI.
- Existing profiles are never overwritten; a changed description in the YAML
  does not update an already-loaded agent. Editing through the dashboards or
  loading a differently named profile is the supported path.
- Profiles are not visible in `--list-agents` until a laboratory contains them;
  the populate screen is the catalog view.

## Alternatives considered

- **Insert rows directly from a Makefile shell recipe**: rejected; it bypasses
  domain validation and transaction boundaries.
- **Extend `--new-agent` with non-interactive flags**: rejected; it would add a
  second input contract for every field and weaken the A-09 decision.
- **Embed the roster in Rust source**: rejected; the product owner asked for a
  data file, and data changes should not require a rebuild.
- **Create a dedicated preset laboratory**: rejected after the populate screen
  was requested; a forced laboratory adds an unrelated object and hides the
  catalog semantics.
- **Update existing profiles on reload**: rejected; silent overwrites of
  user-edited profiles are surprising. The initial scope is create-and-skip.
