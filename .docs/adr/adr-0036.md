# ADR-0036: Automatic memory generation

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amends: ADR-0022 (generation and authorship only)
- Amended by: ADR-0046 (manual laboratory and project surface)

## Context

ADR-0022 made memories immutable, user-authored context. The product owner now
wants memories to be built automatically while the laboratory, projects, and
agents take shape and while agents work on tasks. The user-facing memory
commands are removed by ADR-0035. The storage model, scope constraints, and
bounded prompt inclusion remain useful.

Automatic writes must not turn planning into a second uncontrolled feature:
they must be bounded, must not silently change an action's outcome, and must
never store credentials.

## Decision

1. **Authorship.** Memories are application-managed. The model does not choose
   what to store; the application decides from validated events.
2. **Deterministic structural memories.** Creating a laboratory, an agent, or a
   project writes a short memory in the matching scope:
   - laboratory: the laboratory name;
   - agent: the agent name, role, skills, and laboratory memberships;
   - project: the project name and canonical GitHub source when present.
   The text contains no CV, description, credential, or model output.
3. **Planning summary.** A successful planning run with stories makes one
   additional bounded provider call. The application asks for one plain-text
   paragraph of at most 600 characters summarizing the request and resulting
   stories, then stores it as a project memory prefixed `Planning summary:`.
   The call uses one attempt, a 90-second deadline, 256 output tokens, and the
   configured model. Its failure, cancellation, or invalid/secret-containing
   response is ignored; the request remains `PLANNED` and no memory is stored.
4. **Best effort.** Automatic memory insertion never fails the triggering
   command. A full scope (20 memories), oversized/empty text, or credential
   detection skips the write. Existing memories are retained and continue to
   enter prompts.
5. **Security.** The planning summary prompt contains only the project name, a
   bounded request excerpt, and story titles/descriptions. It is delimited as
   data, uses the same provider credential path as planning, and its output is
   treated as untrusted memory content. It is never logged or placed in the
   database audit metadata.
6. **Observability.** Successful automatic writes record the existing
   `MemoryCreated` event with the memory identifier. No content is recorded.
7. **Scope.** No user command lists, creates, or deletes memories. Memory
   deletion follows owner cascades. Changing automatic content later requires a
   new decision.

## Consequences

- Memories accumulate without user effort and reflect real project evolution.
- A successful planning cycle costs a second, small provider call; failures do
  not affect the request outcome.
- Memory scopes can fill up; further automatic writes are skipped until the
  owner is deleted (there is no manual cleanup command).
- The 8 KiB prompt cap still limits the effect of accumulated memories.
- Existing manual memories remain valid and are not rewritten.

## Alternatives considered

- **Only deterministic memories**: rejected by the product owner; planning
  summaries should capture task work.
- **Model decides what to remember during planning**: rejected; it would add an
  unbounded decision surface and a second output schema.
- **Fail planning when the summary fails**: rejected; the plan is already
  committed and useful.
- **Delete oldest memory when the scope is full**: rejected; silent history
  loss without user visibility.
- **Keep manual commands alongside automatic writes**: rejected by ADR-0035.
