# ADR-0054: Project source types and isolated folder import

- Status: Accepted
- Date: 2026-11-16
- Supersedes: —
- Superseded by: —
- Amends: ADR-0025 (project source field), ADR-0032 (project workspace)
- Related: ADR-0050 (git-worktree execution)

## Context

Projects currently carry an optional GitHub URL. A project without a source has
no checkout under `.workspace`, and the real execution workflow cannot prepare
a git worktree for it. The product owner wants an explicit project source type:

1. **GitHub source** — the existing clone behavior.
2. **Folder source (without version control)** — a local folder that the user
   selects, with no Git repository required at the origin.

The execution model creates one git worktree per story inside the workspace and
never writes outside `.workspace` (ADR-0050). Using the original folder in place
would break that isolation and allow model-proposed actions to modify the
user's files. Copying a folder without version control would create a checkout
where `git worktree` cannot run.

The product owner chose the isolated option: copy the folder into
`.workspace/<project-id>` and initialize a local git repository only inside the
copy. The original folder is never modified and needs no version control.

## Decision

1. **Source model.** A project has one source: `none` (legacy projects only),
   `github`, or `folder`. The domain exposes `ProjectSource` and a validated
   `FolderSource`. A folder source is an absolute path of at most 4,096
   characters, trimmed, without control characters, and not a filesystem root.
2. **Storage.** Schema v12 adds the nullable `projects.folder_source` column.
   Existing rows migrate with `NULL`; a project with no source keeps both
   columns `NULL`. The application never writes both columns for one project.
   The stored folder path is the canonical path resolved at creation time.
3. **GitHub source unchanged.** A GitHub project still validates the canonical
   URL, clone settings, and global credential, clones into a temporary
   directory, and renames it to `.workspace/<project-id>`. No behavior changes
   to ADR-0032.
4. **Folder import.** A folder project is prepared before the project row is
   inserted:
   - Resolve the source with `canonicalize`; reject a missing path, a
     non-directory, a non-UTF-8 path, and a path that is the workspace root,
     inside it, or an ancestor of it.
   - Reject symbolic links and special files anywhere in the tree. Skip every
     entry named `.git`, so an accidental nested repository is not copied.
   - Bound the copy to 100,000 entries, 1 GiB of file content, and a depth of
     64. A limit violation fails closed and creates no project.
   - Copy regular files and directories into a private temporary directory
     under the workspace root.
   - Run `git init`, `git add -A -f`, and an initial commit (empty allowed)
     inside the copy, with a fixed local identity and no push, fetch, network,
     or credential. Force-adding preserves files that a copied `.gitignore`
     would otherwise hide from the initial worktree.
   - Rename the prepared copy to `.workspace/<project-id>`. On any failure,
     remove the temporary directory. If the database insert fails, remove the
     final directory.
5. **Atomicity.** The folder is fully copied and committed before the project
   row is written. A failed import or insert leaves no project row and no
   workspace directory.
6. **No credentials or network.** Folder import never reads the GitHub
   credential, never runs a network operation, and never sends source files to
   the provider. The copied files are project data in the local workspace.
7. **CLI.** `--new-project` accepts `--folder-source <path>` as an alternative
   to `--github-source <url>`. The two modifiers are mutually exclusive.
   Providing a source modifier without `--new-project` is a usage error. No
   modifier keeps the legacy no-source project.
8. **Dashboard.** The New project form gains a source choice (`None`, `GitHub`,
   `Folder`) and one source field whose value is validated against the choice.
   The Projects table, creation output, project opening output, and Kanban
   header show the source kind and detail.
9. **Tests.** Domain tests cover folder path validation. Database tests cover
   schema v12, round-tripping, and migration preservation. Workspace tests
   cover copy fidelity, `.git` exclusion, initial commit, empty folders,
   symlink rejection, and bounds. CLI tests cover mutually exclusive modifiers,
   folder creation without a GitHub credential, failure atomicity, and display.
   Dashboard tests cover the source choice and a folder project creation.

## Consequences

- Folder projects can use the same isolated worktree execution as GitHub
  projects, while the user's original folder remains untouched and VCS-free.
- The copy is a full duplicate: disk usage grows with the source size, and the
  initial commit stores the copied content inside `.workspace`.
- Files ignored by a copied `.gitignore` are force-added to the initial commit
  so the first worktree contains them.
- Symlinks and special files are unsupported in folder sources; the error is
  explicit and no partial project is created.
- The stored folder path is metadata and may become stale if the original
  folder moves. The workspace copy remains usable.
- The workspace and its local repository are disposable, ignored by git, and
  can be removed with `make clean-workspace`.
- Legacy projects without a source remain readable and display as `none`; they
  still cannot run worktree execution.

## Alternatives considered

- **Use the original folder in place**: rejected; it violates the isolation
  guarantee and lets model-proposed commands write to user files.
- **Copy without initializing git**: rejected; `git worktree` cannot run, so
  real story execution would be unavailable.
- **Initialize git in the original folder**: rejected; it modifies user data and
  contradicts "without version control".
- **Follow symbolic links during the copy**: rejected; symlinks can escape the
  source tree and the workspace.
- **Force a GitHub source for every project**: rejected; local folders are the
  requested second type and are useful for prototypes.
- **Store a relative folder path**: rejected; the path is resolved once and the
  canonical absolute path is stable for display and audit.
