- Supersedes: ADR-0005

## Context

The product owner requires readable, colored, keyboard-driven Unix-style
dashboards for laboratories, projects, agents, and settings. ADR-0005 forbade
ANSI color and full-screen TUI, and ADR-0009 fixed a long-flag command surface.
The feature plan `00001-feat-interactive-dashboards.md` defines the desired
experience, safety rules, and task checklist.

The product remains a local, text-only CLI. Dashboards are a presentation layer
over existing application use cases; they must not add provider calls, change
authorization, or expose credentials.

## Decision

1. **Command surface.** Add the subcommands `labs`, `projects`, `agents`, and
   `settings`. A bare `vlab` opens a home dashboard when both stdin and stdout
   are terminals; otherwise it prints help. The old flags may remain as a
   deprecated compatibility shim until the feature’s removal task.
2. **Interactive presentation.** In a terminal, group subcommands open a
   full-screen dashboard with a header, a selectable paginated body, and a
   bottom action bar. `--plain` and non-TTY output use the existing width-aware
   plain renderer with no cursor control or color.
3. **Dependencies.** Use `ratatui` for layout/widgets and its re-exported
   `crossterm` backend for terminal setup and events. Both are pinned and
   recorded in `.docs/DEPENDENCIES.md`. No other TUI framework is introduced.
4. **Terminal lifecycle.** Use the library’s alternate-screen/raw-mode helpers
   or an equivalent RAII guard. Restore the terminal on success, error, panic,
   SIGINT, and editor/wizard suspension. Never leave the cursor hidden.
5. **Color.** Use semantic tokens and 256-color with 16-color and monochrome
   fallbacks. Honor `NO_COLOR`, `TERM=dumb`, `--no-color`, and non-TTY output.
   Color is never the only signal; pair it with text or symbols.
6. **Safety.** All mutations call the existing application use cases and
   confirmation rules. Destructive modals show the exact target. `Esc`
   cancels. No credential value is rendered. Stored/model text is sanitized
   before display. Dashboards make no provider calls and no writes from
   navigation alone.
7. **Testing.** Render with `TestBackend` at fixed sizes, test the input state
   machine without a terminal, and test non-TTY/plain paths through the CLI.
   PTY tests are added when the harness is available; a missing PTY must not
   make the suite flaky.
8. **Compatibility.** Removing the old flags is a separate checklist item with
   help-snapshot and documentation updates. Until then, both surfaces map to
   the same use cases.

## Consequences

- Output is more usable for humans while `--plain` remains scriptable.
- The binary gains a UI dependency and terminal-control code; supply-chain,
  panic-safety, and accessibility tests become mandatory.
- The old “no ANSI ever” contract is replaced by a conditional contract:
  no ANSI in plain output, errors, logs, or non-TTY streams.
- ADR-0005 is superseded; ADR-0009 and ADR-0021 are amended for the new
  subcommand and dashboard layout.

## Alternatives considered

- **Crossterm-only custom renderer**: smaller dependency surface but more
  layout, widget, and test code; rejected for the initial dashboard scope.
- **Keep plain output and add color only**: rejected by the product owner;
  dashboards and keyboard actions are required.
- **Keep long flags and add dashboards behind a mode flag**: rejected as a
  second, confusing interface; subcommands are the target.
- **Mouse-first or web UI**: rejected; text terminal first.
