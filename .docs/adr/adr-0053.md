# ADR-0053: Laboratory populate screen with a two-pane agent transfer

- Status: Accepted
- Date: 2026-11-16
- Supersedes: —
- Superseded by: —
- Amends: ADR-0038 (dashboards), ADR-0045 (read-only floor), ADR-0034
  (planning roster)

## Context

ADR-0052 adds a reusable catalog of preset agent profiles. Creating a profile
is not enough: the operator must be able to put available profiles into a
laboratory. The existing dashboard can open a laboratory, inspect its members,
and assign members to projects, but it has no way to add or remove laboratory
memberships. Doing it through a sequence of prompts would be slow and would
make it easy to miss the one-Tech-Lead rule.

The product owner asked for a user-friendly, intuitive option in the
laboratory: all available agents on one side and the agents currently in the
laboratory on the other. The existing floor is documented and tested as
read-only (ADR-0045); extending it with writes would contradict that decision.

## Decision

1. **Entry points.** The Laboratories dashboard gains a **Populate** action,
   bound to `o`, for the selected laboratory, whether or not it is active. The
   Lab floor gains the same key for the active laboratory. The floor scene
   remains read-only: `o` only navigates to the separate editor.
2. **Two-pane transfer screen.** The screen shows two bordered panes:
   **Available agents** (all active profiles not currently in the laboratory)
   and **In this laboratory** (the laboratory's active members). Each row shows
   the agent name, role, and a short profile description; the selected row is
   highlighted. Both panes scroll and show counts.
3. **Staged changes.** `Tab` or `←/→` switches pane, `↑/↓` moves the selection,
   and `Enter` or `Space` moves the selected agent to the other pane. Nothing
   is written until `s` saves. `Esc` leaves the screen; when there are unsaved
   moves, it asks for confirmation before discarding them.
4. **Validation on save.** Saving requires at least one active member and
   exactly one active `lead`. Every selected identifier must resolve to an
   existing active profile. A failure keeps the screen open with a clear
   message and writes nothing.
5. **Atomic membership diff.** A new
   `Directory::update_lab_memberships(lab, add, remove)` port applies the
   additions and removals in one transaction. Unchanged memberships keep their
   `joined_at` timestamp. Archived memberships are not part of the active set
   and are preserved.
6. **Catalog read model.** A new `Directory::all_agents()` query returns all
   profiles; the screen filters archived profiles. No schema change is needed.
7. **No provider work.** The screen performs local reads and writes only. It
   does not call the provider, start a workflow, or change project assignments.
8. **Audit.** A successful save records one `lab_populated` event with the
   laboratory entity. The event carries no agent names, skills, or free text.
9. **Tests.** Application tests cover the available/member partition,
   add/remove diffs, archived exclusion, missing agents, and the exactly-one
   lead rule. A dashboard test opens Populate, moves an agent, saves, and
   verifies the rendered counts and database membership. A database test
   verifies the transaction and preserved `joined_at` for unchanged members.

## Consequences

- The operator can staff a laboratory with a few keystrokes and see both sides
  before committing.
- The one-Tech-Lead rule is enforced at save time, so a partially edited roster
  cannot corrupt a valid laboratory.
- The screen is available without activating the laboratory, which avoids
  changing global context just to edit a roster.
- The floor stays a pure read model.
- Membership changes are visible only after `s`; unsaved changes are discarded
  on request, not silently written.
- A laboratory with zero agents cannot be saved, matching the structural
  requirement. To build a new roster, add the Tech Lead and at least one other
  agent before saving.

## Alternatives considered

- **Write on every move**: rejected; a mistaken keypress could remove the Tech
  Lead, and there would be no single confirmation point.
- **A one-item picker modal**: rejected; it hides the current roster and makes
  repeated additions slow.
- **Edit memberships on the floor**: rejected; ADR-0045 defines the floor as
  read-only and its scene is a visualization, not a form.
- **Auto-create a laboratory from the preset file**: rejected in ADR-0052;
  the catalog and the laboratory roster are separate concerns.
- **Allow saving without a Tech Lead**: rejected; the laboratory would fail its
  structural validation immediately after an apparently successful save.
