# ADR-0023: Schema v3 for projects, requests, stories, and planning states

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

WP-4 needs durable projects within a laboratory and the tables that WP-5 will
populate during planning. The specification §3.2, §8, §9.3, and §10 define
project ownership, request status, story fields, priority, complexity, state,
assignments, and due dates. `ADR-0002`/`ADR-0016` fix SQLite and migrations;
`ADR-0022` fixes scoped memories. The schema must land before planning code so
WP-5 never introduces tables it needs for basic persistence.

## Decision

1. **Migration.** `migrations/0003_projects_requests_stories.sql` adds
   `projects`, `requests`, `stories`, and `memories` in one schema v3
   migration.
2. **Projects.** `projects(id, lab_id, name, created_at, updated_at)` with a
   foreign key to `labs` and `ON DELETE CASCADE`; names are trimmed 1–100
   characters.
3. **Requests.** `requests(id, project_id, content, status, questions_json,
   error_code, error_message, planning_started_at, created_at, updated_at)`.
   Status is constrained to `TODO`, `PLANNING`, `PLANNED`,
   `NEEDS_CLARIFICATION`, or `FAILED`. Planning errors and questions are
   bounded, validated data written by WP-5; no prompt or provider body is
   stored.
4. **Stories.** `stories` stores the required fields from §9.3;
   `priority` is `low|medium|high`, `complexity` is `small|medium|large`, and
   `state` is `TODO|IN_PROGRESS|IN_REVIEW|BLOCKED|DONE`. `assigned_agent_id`
   references `agents` with `ON DELETE SET NULL`; agent deletion archives
   profiles instead of deleting them.
5. **Memories.** The table and its rules are recorded in ADR-0022.
6. **Cascades and indexes.** Laboratory deletion cascades to projects,
   requests, stories, and memories; project deletion cascades to its requests,
   stories, and memories. Indexes cover project ownership, request status,
   story state, story assignment, and memory scopes.
7. **Timestamps and dates.** Timestamps are RFC 3339 UTC text generated by
   SQLite; story due dates are `YYYY-MM-DD` text and are computed locally in
   WP-5.
8. **Migration safety.** The v2 → v3 test preserves laboratories, agents,
   memberships, application state, and event history. The migration is
   forward-only and refuses newer schemas through the existing runner.

## Consequences

- WP-5 can persist requests and stories into a tested schema without changing
  the migration layer again.
- Deleting a laboratory or project is a single cascade with no orphaned rows.
- Empty planning results are represented by request status, not by partial
  stories; the database permits zero stories for a request until WP-5 decides
  the terminal status.
- Archived agents remain resolvable and story assignments remain historical.
- The Kanban reads states that exist before any transition command; the
  initial release creates only `TODO` stories and documents that limitation.

## Alternatives considered

- **Add tables package by package**: rejected; WP-5 would introduce schema
  while implementing provider behavior, making migration and test failures
  harder to isolate.
- **Separate `questions`/`errors` tables**: rejected for the initial release;
  bounded JSON/text on the request row is simpler and has one owner.
- **Delete agents and null assignments**: rejected; A-15 preserves historical
  identity through archival.
- **Store due dates as timestamps**: rejected; the specification requires
  calendar dates and local calculation.
- **Store memory content in a generic JSON blob**: rejected; typed scope and
  foreign keys prevent cross-owner leakage.
