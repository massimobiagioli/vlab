# ADR-0064: Non-blocking startup resume

- Status: Accepted
- Date: 2026-11-17
- Supersedes: —
- Superseded by: —
- Amends: ADR-0049 (startup resume), ADR-0061 (background worker)

## Context

ADR-0049 resumed due schedules and pending story execution before opening the
interactive dashboard. It also printed `Resuming pending workflow...` to stderr
while the terminal had not yet entered dashboard mode. When a workflow was
pending, `vlab` appeared stuck on that line: the dashboard did not open, the
operator could not see the application working, and every startup path that
touched pending work was synchronous.

The product owner requires the tool to open immediately and to show background
activity in the dashboard instead of blocking on a pre-TUI message. The
application already has one serial background worker for queued requests
(ADR-0061); startup work belongs there too.

## Decision

1. Remove the pre-TUI `resume_pending_workflow` call from the bare `vlab`
   entry point. The dashboard opens immediately.
2. Before draining queued requests, the in-process worker performs one bounded
   startup pass: due schedules for the current project, then the existing
   bounded workflow for pending `IN_PROGRESS`/`IN_REVIEW` stories. It uses the
   same budgets, cancellation token, settings, and workspace environment.
3. Progress is reported as `Background:` status events in the dashboard:
   checking, schedule summary, resume message, workflow summary, warnings, and
   completion. No message is written to stderr before the terminal starts.
4. The startup pass is one-shot per process. There is no timer, daemon, or new
   background loop. `--run-schedules` and `--run-queue` remain explicit
   bounded commands.
5. Quitting cancels the shared token; the worker checks it during the startup
   pass and before selecting queued requests. A provider or workflow failure is
   reported and does not prevent the dashboard from continuing.
6. No schema, migration, dependency, provider contract, or trust-boundary
   change. The startup pass is read/write through the existing bounded
   application use cases, not a new execution path.

## Consequences

- `vlab` opens at once even when a workflow is pending; the operator sees the
  dashboard and a `Background:` status while the work runs.
- Startup work and queued requests share one worker, so they cannot run in
  parallel or multiply provider calls.
- The dashboard must tolerate a status line that changes from background
  progress to request progress; reloads follow the existing worker events.
- A quit during the startup pass cancels the pass; stale `PLANNING` recovery
  remains the next-start safety net.

## Alternatives considered

- **Keep the synchronous resume but print a different message**: rejected; the
  blocking behavior was the defect.
- **Spawn a separate startup thread plus the queue worker**: rejected; it would
  create two concurrent provider paths and duplicate budget/cancellation logic.
- **Move startup resume into a daemon**: rejected; VLab remains a local CLI.
- **Skip startup resume entirely**: rejected; due schedules and pending stories
  must still resume without manual commands.
