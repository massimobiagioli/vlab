# ADR-0056: Project interaction history with recaps

- Status: Accepted
- Date: 2026-11-16
- Supersedes: —
- Superseded by: —
- Amends: ADR-0028 (interaction metadata remains content-free)
- Related: ADR-0037 (feature plans), ADR-0050 (workflow execution)

## Context

VLab already records real agent collaboration while a project runs:

- the Tech Lead plans a request into stories and assigns them;
- the assignee executes a story in an isolated worktree and writes a bounded
  work summary;
- a reviewer, normally a QA agent or the Tech Lead, reviews the work and writes
  a bounded review outcome.

The existing `interactions` table is deliberately content-free metadata for
provider calls and has no project scope or recap. Work and review summaries are
stored in `story_outcomes`; planning has the request row and the resulting
stories. The product owner wants a project-level history of agent interactions
where every entry has a recap, on a separate page.

VLab does not run free-form multi-agent chat and ADR-0050 forbids unbounded
autonomous orchestration. The history must therefore describe the collaboration
that actually happens, not invented conversations.

## Decision

1. **Interaction entries are a read model.** A project interaction entry is one
   of:
   - `planning`: the Tech Lead and the agents assigned by one request;
   - `work`: one assigned agent working on one story;
   - `review`: one reviewer evaluating one assignee's story work.

   Entries are derived from `requests`, `stories`, `story_outcomes`, and agent
   rows. No new recap table is created and the content-free `interactions`
   table is not changed.
2. **Planner attribution.** Schema v13 adds the nullable
   `requests.planned_by_agent_id` foreign key. Planning sets it when the request
   enters `PLANNING`; existing requests remain `NULL`. This records the actual
   Tech Lead even if the laboratory lead changes later.
3. **Recap rules.**
   - Planning: the request content plus the resulting stories and assignees,
     the clarification questions, or the stable failure code, capped at 4,000
     characters.
   - Work: `story_outcomes.work_outcome` when present; otherwise a deterministic
     state recap such as "work in progress" or "blocked".
   - Review: `story_outcomes.review_outcome` plus accepted/rejected when
     present; otherwise a deterministic pending or not-reviewed recap.
4. **Every entry has an outcome.** `success`, `failure`, or `pending`. Planning
   uses the request status and error code; work uses the presence of a stored
   work outcome and the story state; review uses the stored decision.
5. **Separate page.** A new read-only dashboard screen lists the current
   project's entries newest first: time, kind, participants, reference, outcome,
   and a truncated recap. `Enter` opens a scrollable detail with the full recap.
   `r` reloads; `Esc` returns to the originating screen. It is available from
   the Projects dashboard for the selected project and from the Kanban board
   for the current project.
6. **Read-only and bounded.** The page performs one local read and never calls
   the provider, starts a workflow, writes data, or changes a story. Recaps are
   rendered only after sanitization and are bounded by the existing work/review
   limits or the 4,000-character planning cap.
7. **Audit.** The page adds no audit event; it exposes existing project data.
   The content-free `interactions` table remains the source for provider-call
   metadata.
8. **Tests.** Schema tests cover the planner column and migration preservation.
   A database/app test seeds a request, stories, and an outcome and verifies
   planning, work, and review entries, participants, recaps, outcomes, and
   ordering. Dashboard tests cover rendering, scrolling, the detail dialog, and
   the Projects/Kanban entry points.

## Consequences

- Operators can see how a project was planned, executed, and reviewed without
  opening each story.
- The history is accurate for the agents who actually acted; planner
  attribution survives later lead changes.
- No duplicate content is stored: work and review recaps remain the bounded
  summaries already persisted for the story.
- Existing databases show no planner for historical requests until a future
  migration or manual backfill; their planning entries still list assignees.
- The page is not a chat log. Free-form agent-to-agent conversations would need
  a separate decision and would conflict with the no-unbounded-orchestration
  guardrail.

## Alternatives considered

- **Store a new `agent_interactions` table with recap text**: rejected; it would
  duplicate bounded work/review summaries and add a write path without a new
  source of truth.
- **Use the content-free `interactions` table for recaps**: rejected; ADR-0028
  keeps provider-call metadata content-free.
- **Show only provider calls**: rejected; it lacks participants, story context,
  and a meaningful recap for the operator.
- **Add free-form agent chat**: rejected; it is a different product capability
  and conflicts with ADR-0050.
- **Use the current laboratory lead for every historical planning entry**:
  rejected; it becomes wrong when the lead changes.
