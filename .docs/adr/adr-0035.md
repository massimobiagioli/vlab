# ADR-0035: Remove manual memory commands

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —
- Amends: ADR-0022 (command surface only)

## Context

Memories were exposed through `--new-memory`, `--list-memories`, and
`--delete-memory` with a laboratory, project, or agent scope. The product owner
now wants memory handling to be automatic and no longer part of the user-facing
command surface. The storage model and the bounded prompt-context rules remain
valid, and existing rows must not be lost.

## Decision

1. Remove the three memory commands and their `--for-lab`, `--for-project`,
   and `--for-agent` selectors from the CLI, help, and dispatch.
2. Keep the `memories` table, the domain types, the planning selection, the
   secret-content rejection, and the cascade rules. Existing rows remain
   readable by planning.
3. Do not add automatic memory creation in this change. "Automatic" means the
   user no longer manages memories manually; a future specification will define
   what the application writes automatically. Until then, the planning context
   simply uses the rows that exist.
4. Update the CLI reference, README, playbook, specification, and tests so no
   documented command manages memories.

## Consequences

- Users cannot inspect or delete individual memories through VLab; manual SQL
  editing remains possible outside the product surface.
- Existing memories keep influencing planning through the documented bounded
  selection.
- Removing commands is a breaking CLI change and requires script updates.
- The data-retention policy still covers memory rows; only the command surface
  changed.

## Alternatives considered

- **Keep read-only commands**: rejected by the product owner; memories should
  not be a user-managed surface.
- **Delete memory rows**: rejected; it would destroy context without a
  migration requirement.
- **Implement automatic writes now**: deferred; it needs a separate
  specification and trust analysis.
