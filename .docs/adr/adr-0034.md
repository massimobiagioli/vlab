# ADR-0034: Project agent assignments and planning roster

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

Laboratory membership established which agents exist in a laboratory, and
planning assigned stories to any active laboratory member. The product owner
requires assigning agents to the current project and expects that assignment
to determine who works on it. A project therefore needs its own membership
set, and planning must use it rather than the whole laboratory.

## Decision

1. **Schema.** Migration `0006_project_agents.sql` adds
   `project_agents(project_id, agent_id, created_at)` with a composite primary
   key and cascading foreign keys to `projects` and `agents`. Both directions
   are indexed for lookup and deletion.
2. **Command.** `--assign-agent <agent-id>` uses the current project and
   requires the agent to be an active member of the project's laboratory.
   Repeating the same assignment is idempotent. Archived agents and agents
   from another laboratory are rejected before insert.
3. **Planning roster.** `--new-request` uses the project's assigned agents when
   at least one assignment exists. If the project has no assignments, it falls
   back to all active laboratory members, preserving the existing behavior for
   projects created before this decision.
4. **Validation.** Assigned agents are filtered through active laboratory
   membership; an assignment to an agent who is no longer a member is ignored
   by planning. If assignments exist but none resolves to an active member, the
   request fails with an actionable precondition error rather than silently
   planning with an empty roster.
5. **Lifecycle.** Project deletion cascades assignments. Agent deletion
   cascades assignments. Laboratory deletion reaches them through projects.
   Assignments are not credentials and contain only identifiers and a
   timestamp.
6. **Scope.** The command assigns existing agents; creating agents remains
   `--new-agent`. `--ask` keeps its laboratory/Tech Lead targeting semantics in
   this change.

## Consequences

- Planning can be scoped to the team actually working on a project.
- A project with no assignments keeps working with the laboratory roster.
- Users must assign agents before planning if they want a restricted roster.
- The board does not yet show the assigned roster; it can be added without a
  schema change.

## Alternatives considered

- **Use laboratory membership only**: rejected; it cannot express a project
  team.
- **A single project owner**: rejected; planning needs a roster.
- **Reuse story assignments as membership**: rejected; membership must exist
  before planning.
- **Require assignments for every project**: rejected; it would break existing
  projects and the fallback is harmless.
