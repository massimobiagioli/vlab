# ADR-0057: Recurring project task schedules

- Status: Accepted
- Date: 2026-11-16
- Supersedes: —
- Superseded by: —
- Related: ADR-0050 (bounded execution), ADR-0044 (request intake), ADR-0056
  (project interaction history)

## Context

The product owner wants recurring project tasks that an agent can own, for
example a periodic security review or a framework/library update. The schedule
must be visible and manageable on a separate page.

VLab is a local CLI, not a daemon, and ADR-0050 forbids unbounded autonomous
execution or model-chosen control flow. A schedule must therefore not run
free-form commands on its own. It must create the same bounded work item that a
human request creates and then use the existing planning and workflow path.

## Decision

1. **Schedule model.** A schedule belongs to one project and one active
   laboratory member. It has a title, a single-line task request of at most
   2,000 characters, an interval (`daily`, `weekly`, or `monthly`), an enabled
   flag, `next_run_at`, `last_run_at`, an optional last request, and an optional
   stable last error code.
2. **Storage.** Schema v14 adds the `schedules` table with project cascade
   deletion. No prompt, provider response, file content, or command output is
   stored beyond the operator-provided task text.
3. **Creation.** The Projects dashboard opens the Schedules page with `s`. The
   page can create a schedule with a form (title, task request, interval, owner
   agent), pause/resume it, delete it after confirmation, and show its details.
   The first run is one interval after creation.
4. **Execution.** Due schedules run when the dashboard starts and through the
   hidden `--run-schedules` command. The application processes at most three
   due schedules per pass. Each due schedule creates a normal request through
   `requests::plan`; when the plan succeeds, the existing bounded workflow runs.
   The owner name is included in the request text, but the Tech Lead still
   performs assignment and validation.
5. **Bounds and failure handling.** A schedule with an inactive owner is not
   executed; it records `agent_inactive` and advances. Planning or workflow
   failures record a stable code, update `last_run_at`, advance `next_run_at`,
   and never retry in a loop. A cancelled run advances like any other run.
6. **Read-only page execution.** The Schedules page never calls the provider.
   It only creates, edits state, and deletes schedule rows. Execution is an
   explicit startup/CLI action, not a background process.
7. **Audit.** Creating, updating (pause/resume), and deleting a schedule record
   `schedule_created`, `schedule_updated`, and `schedule_deleted` events with
   the schedule identifier only. No task text or provider content is recorded.
8. **Tests.** Database tests cover creation, due ordering, run advancement,
   inactive owners, pause/resume, and deletion. The dashboard test creates,
   pauses, and deletes a schedule. CLI tests cover the hidden run command.

## Consequences

- An agent can own a recurring project task without granting the model new
  authority: the task still becomes a bounded request and workflow.
- Schedules run on dashboard startup or when `--run-schedules`/`make
  run-schedules` is invoked. VLab does not run a background daemon; a cron or
  launch agent can call the hidden command if unattended periodic execution is
  required.
- A missed interval runs once on the next pass; there is no catch-up storm.
- The owner attribution is advisory: the Tech Lead may assign the resulting
  stories to other suitable agents.
- The schedule page shows the last request status and error code, so failures
  are visible without reading logs.
- Task text is project data and is sanitized when rendered; it is never sent to
  a provider except through the normal planning request that the schedule
  creates.

## Alternatives considered

- **Run arbitrary model-chosen commands on a timer**: rejected; it violates the
  bounded-execution and no-unbounded-orchestration guardrails.
- **Run the full workflow inside the dashboard event loop**: rejected; it would
  block the UI and make provider cost unpredictable. Startup/CLI is explicit
  and bounded.
- **Store the last request status on the schedule**: rejected; it duplicates
  request state. The page joins the last request row instead.
- **Use free-form intervals**: rejected for the initial release; daily, weekly,
  and monthly are unambiguous and bound the minimum interval.
- **A daemon process**: rejected; VLab is a one-shot local CLI.
