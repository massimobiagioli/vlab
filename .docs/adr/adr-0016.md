# ADR-0016: SQLite schema v1 and the synchronous database adapter

- Status: Accepted
- Date: 2026-11-12
- Supersedes: —
- Superseded by: —

## Context

[ADR-0002](adr-0002.md) selects SQLite through SQLx, one connection, foreign
keys, versioned migrations, private permissions, and no credentials in the
database. WP-2 introduces the first schema (`app_state`, `events`), the
migration runner, the connection policy, and the audit-event sink. `STACK.md`
requires a verified engine and database library. The plan's Appendix B lists
the intended columns; WP-2 also has to record migration versions in the audit
log.

## Decision

1. **Dependencies and engine.** Add `sqlx` 0.9.0 with default features off and
   `runtime-tokio`, `sqlite`, `migrate`, and `macros`, and `tokio` 1.54.1 with
   `rt` and `time`. The build bundles SQLite 3.54.1 through
   `libsqlite3-sys` 0.39.1, so no system SQLite version influences behavior.
   The driver crate is vendored temporarily to allow the fixed engine
   (ADR-0017). Both crates are recorded in
   [`../DEPENDENCIES.md`](../DEPENDENCIES.md).
2. **Connection policy.** One pooled connection. Every connection sets
   `PRAGMA foreign_keys = ON` and a 5-second `busy_timeout`; the adapter reads
   both back and refuses the connection if they differ. Journal mode is
   `DELETE` (WAL disabled, D-7) and `synchronous = FULL`.
3. **Private storage.** The parent directory is created or verified private
   (`0700`, fail closed). The database file is created with `0600`, a planted
   link is refused, and an existing regular file is tightened to `0600` and
   verified.
4. **Synchronous facade.** `infra::db::Database` owns a current-thread Tokio
   runtime and exposes blocking methods plus `transaction`. The CLI is a
   one-shot process, so this keeps the application layer free of async
   plumbing while the driver remains async. The pool is exposed for tests and
   for later adapters; repositories remain typed.
5. **Migrations.** Migrations are embedded with `sqlx::migrate!`, are
   forward-only, and run in transactions. The runner also maintains
   `PRAGMA user_version`; opening a database whose version is newer than the
   binary supports fails with a classified error. A target older than the
   database and a modified migration history are refused. A failed migration
   leaves no partial schema.
6. **Schema v1.** Two `STRICT` tables:
   - `app_state(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL)`;
   - `events(id, run_id, action_id, kind, entity_type, entity_id, outcome,
     error_code, duration_ms, attempt, provider, model, schema_from,
     schema_to, created_at)`.
   Indexes cover `events(run_id)`, `events(entity_type, entity_id)`, and
   `events(created_at)`. Timestamps are generated by SQLite
   (`strftime('%Y-%m-%dT%H:%M:%fZ','now')`) so they are RFC 3339 UTC with no
   local-time or DST dependency.
7. **Audit persistence.** `Database` implements the typed `EventSink`; the
   SQL insert has no free-text column. `schema_from` and `schema_to` are added
   to record the version pair of `migration_applied`. This is a deliberate,
   typed extension of the column list in the implementation plan's Appendix B:
   the plan requires the versions to be recorded, and no other column may
   carry them without abusing an unrelated field.
8. **Error classification.** SQLite results become `StorageError` variants
   (`Locked`, `PermissionDenied`, `Corrupt`, `DiskFull`, `NewerSchema`,
   `Migration`, `SchemaMismatch`, `Io`, `Operation`). SQL, driver messages,
   stored values, and file contents are never retained, so errors are safe to
   render and log. The CLI maps all of them to exit code 1.
9. **Schema policy.** Application tables must not have credential-bearing
   column names. The rule is unit-tested and checked against the migrated
   schema in `tests/db_schema_policy.rs`; `app_state.key` is the documented
   exception (it holds a state name).

## Consequences

- `--show-settings` and `--edit-settings` still touch neither the database nor
  the network; the first database use arrives with WP-3.
- The database is single-writer by construction; a competing writer waits up
  to the busy timeout and receives an actionable lock error.
- The engine is fixed at build time, which makes behavior reproducible but
  requires a dependency update to pick up SQLite fixes.
- Adding a table, column, or index requires a new migration and an update to
  [`../data-retention.md`](../data-retention.md).
- The synchronous facade must not be called from inside an async task on the
  same runtime; repositories document this and later packages interact through
  the typed methods.

## Alternatives considered

- **`rusqlite`**: rejected by `STACK.md`, which mandates SQLx.
- **Async application layer now**: rejected as unnecessary complexity for a
  one-shot CLI; the synchronous facade can be narrowed or widened later
  without changing the schema.
- **WAL mode**: rejected because no measured concurrency requirement exists
  and WAL is unsafe on some network filesystems (D-7).
- **`PRAGMA user_version` only, without `_sqlx_migrations`**: rejected; SQLx
  migration history catches edited and missing migrations.
- **A separate `migrations` audit table**: rejected; the typed event log
  already records what ran, and duplicating it adds retention surface.
- **Free-text `detail` in `events`**: rejected; it would let request text,
  prompts, and credentials into durable storage (`SECURITY.md`).
