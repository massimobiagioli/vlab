# ADR-0048: Bounded no-tool story workflow simulation

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0003 (planning-only provider use), ADR-0026 (invocation
  contract), ADR-0038 (read-only stories), ADR-0043 (Kanban detail)
- Amends: `AGENTS.md` §6 and `TECHNICAL-SPECIFICATIONS.md` §2 (automation scope)

## Context

The product owner wants the board lifecycle to be automatic: the human supplies
only the natural-language request, assigned stories move through
`IN_PROGRESS`, then `IN_REVIEW`, and finally `DONE`. The review must be
assigned to a QA candidate, falling back to the Tech Lead. A `DONE` card must
show the outcome.

VLab has no execution engine. Its only model integration is bounded planning,
questions, and a summary; it has no tools and never executes model output
(ADR-0003, ADR-0026, `AGENTS.md` §6). Implementing real code execution would
require shell/filesystem/network tools, a sandbox, and a new security model,
and it remains an explicit non-goal. The product owner selected a bounded
**simulation without tools**: the agents produce textual work and review
outcomes, but no code is executed.

This is a scope change. It must be recorded before implementation and must
preserve strict provider bounds, untrusted-output handling, and content-free
audit metadata.

## Decision

1. **Workflow trigger.** After a planning run commits stories, the application
   runs one fixed workflow for the project's `IN_PROGRESS` stories that have no
   stored outcome. The human supplies only the request; no board action starts
   or advances a story. The workflow is synchronous after planning.
2. **Work phase.** For each story, one provider call is made as the assignee.
   The prompt contains the story title, description, acceptance criteria,
   priority, complexity, project name, and a bounded request excerpt. The model
   returns strict JSON with one `work_outcome` string (1–2,000 characters).
3. **Review phase.** One provider call is made as the reviewer. The reviewer is
   the first active `qa` member of the project roster, or of the active
   laboratory roster when the project roster is empty; if there is no active
   `qa`, the Tech Lead reviews. The prompt contains the story and the work
   outcome; the model returns strict JSON with one `review_outcome` string
   (1–2,000 characters). The review is advisory: it is recorded, but it does
   not create an unbounded rejection loop.
4. **Completion.** When both calls succeed, the application inserts one row in
   `story_outcomes` and sets the story `DONE` in one transaction. The row
   stores the work outcome, review outcome, reviewer identifier, and completion
   time. A `DONE` card detail shows all of them. `IN_REVIEW` is the transitional
   state used while the review call runs; it is committed before the call so a
   crash leaves an inspectable state.
5. **Failure.** A provider or validation failure returns the story to
   `IN_PROGRESS`, records a content-free `workflow_failed` event, and does not
   fail the planning request. A crash between the `IN_REVIEW` commit and the
   outcome leaves the story `IN_REVIEW`; the next run also processes pending
   `IN_REVIEW` stories. No automatic repair loop and no retry of invalid
   output.
6. **Bounds.** At most two calls per story, one attempt per call, 60-second
   attempt timeout, 512 output tokens, and a 240-second total workflow deadline.
   Stories are processed sequentially; when the deadline expires, the remaining
   stories stay in their current state. Each call uses the existing provider
   adapter, transport retry policy, cancellation token, and interaction
   metadata with the new `workflow` kind.
7. **Security.** The workflow has no tools, shell, filesystem, network, or code
   execution. Work and review outcomes are model output, treated as untrusted
   text: validated, sanitized for display, never executed, and never allowed to
   alter policy or state. Prompts exclude CVs, credentials, and unrelated
   projects. Audit events carry identifiers and error codes only; outcomes are
   project data and follow story retention.
8. **Persistence and events.** Schema v9 adds the `story_outcomes` table and
   extends the content-free `interactions.kind` constraint with `workflow`.
   Story lifecycle events (`story_work_completed`, `story_reviewed`,
   `story_completed`, `story_blocked`, `workflow_failed`) carry the story
   identifier and no outcome text. `StoryDetail` gains the optional outcome.
9. **Tests.** Scripted-provider tests cover work and review success, reviewer
   selection (QA then Tech Lead), failure states, bounds, outcome persistence,
   and Kanban detail rendering. No live provider is required.

## Consequences

- The board advances automatically after a request, and `DONE` cards expose a
  work/review outcome.
- A successful assigned story costs two additional provider calls; the total
  workflow is bounded but can be expensive for many stories.
- `DONE` means "the no-tool simulation produced and reviewed textual outcomes",
  not that code was written, tested, or deployed. The UI and documentation must
  say so.
- The product keeps the no-tools/no-execution boundary; real execution remains a
  separate, security-heavy decision.
- `IN_PROGRESS`/`IN_REVIEW` can remain after provider failures; the next
  planning run retries them.

## Alternatives considered

- **Keep planning-only and manual transitions**: rejected by the product owner.
- **Real execution with shell/filesystem tools and a sandbox**: rejected for
  this change; it overturns ADR-0003, the no-tools rule, and the current
  security model.
- **Single call producing both work and review**: rejected; it removes the
  independent reviewer role requested by the product owner.
- **Unbounded review/rework loop**: rejected; it multiplies cost and can never
  terminate. The simulation records the review as advisory.
- **External runner**: viable for real work but adds an API and trust boundary
  beyond this request.
