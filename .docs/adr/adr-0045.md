# ADR-0045: Read-only laboratory floor view

- Status: Accepted
- Date: 2026-11-13
- Supersedes: —
- Superseded by: —
- Amends: ADR-0038 (dashboard screens), ADR-0039 (home navigation)

## Context

The product owner wants a view of the agents cooperating in a laboratory: a
two-dimensional representation of the laboratory with friendly, MSX-like
graphics that are still immediately understandable. An agent that is doing
nothing must show a `(zzz)` speech bubble.

VLab stores laboratories, memberships, project assignments, stories, and
content-free provider interaction metadata. It does not store inter-agent
messages, and it must not imply real-time execution that does not exist. The
planning roster rules already define cooperation: a project uses its assigned
agents, or the whole active laboratory when no assignments exist (ADR-0034).
The view is a presentation concern and must not add provider calls, writes,
tables, or model text (ADR-0028, ADR-0038).

## Decision

1. **Entry and navigation.** Add a full-screen `Lab floor` screen to the home
   dashboard (`Enter` on the item or `5`). `Esc` returns home, `q` quits,
   `↑/↓` select agents, `←/→` page project pods, `Enter` opens the existing
   agent detail, `m` opens laboratory and project memories (ADR-0046), `r`
   reloads, and `?` shows help.
2. **Data.** The view reads the active laboratory only and never writes. It
   shows active agents; archived agents are hidden and counted in the header.
   Project pods come from explicit project assignments. A project with an
   empty roster uses the whole active laboratory, matching planning. Agents
   assigned to no pod sit in a `Lounge` pod. The first active agent with the
   `lead` role is the Tech Lead and is shown at a central coordination desk
   instead of being duplicated in every pod. Open assigned stories determine
   the activity state: zero is idle, one is working, and two or more is
   focused.
3. **Visual language.** The screen is deterministic: no animation, timers, or
   random placement. It uses an MSX-inspired terminal style: a double outer
   frame, a tiled floor, project pods, compact `(◕‿◕)` sprites at narrow sizes,
   two-line block sprites at wide sizes, project accent colors, and cooperation
   connectors from each pod to the Tech Lead desk.
   Idle agents show `(zzz)`. Two working agents of different roles in the same
   project sit next to each other with `( ? )` and `( ! )` bubbles and a
   `⇅` exchange marker. A focused agent leaves the huddle for an isolated
   `focus desk` and shows `(///)` or `(</>)`. Color is never the only signal;
   the project name, `★`, the bubbles, and the desk labels carry the meaning.
   Unicode is used when the locale supports it, with an ASCII fallback.
4. **Legibility.** All stored text is sanitized and width-aware. Pods are at
   least 22 columns and paginate horizontally; a pod that cannot show every
   member shows `+N more`. The selected agent is named in the status line with
   role, project count, open stories, and skills. The global 60×20 terminal
   minimum still applies, with an explicit empty or error state.
5. **Bounds.** The floor adds no dependency, table, migration, provider call,
   or write path; memories are the separate ADR-0046 surface. The view never
   renders model output, credentials, or CVs. It is an interactive-only
   screen; `--plain` and non-TTY output are unchanged.
6. **Tests.** The application read model is unit-tested for assignments,
   whole-lab fallback, lounge, lead selection, archived agents, activity
   states, exchange pairs, and counts. The renderer is tested with
   `TestBackend` at 60×20, 80×24, and 100×30, including the idle bubble,
   exchange bubbles, focus desk, pagination, ASCII fallback, and selection.

## Consequences

- Users get an intuitive overview of who works with whom and who is idle,
  grounded in stored assignments rather than invented activity.
- "Cooperation" means shared project membership and Tech Lead coordination;
  the screen must not be read as a live message trace.
- The TUI gains one screen and a scene renderer, but storage, provider,
  security, and retention behavior are unchanged.
- The scene is an approximation. A future live-execution feature would need a
  separate decision and data source.

## Alternatives considered

- **Force-directed agent graph**: rejected; it is harder to read at terminal
  sizes, harder to test, and loses the 2D laboratory feel.
- **Animated sprites and walking agents**: rejected; animation is
  non-deterministic, adds timers and redraw cost, and complicates tests.
- **Persist inter-agent messages or a live event feed**: rejected; it adds a
  schema, retention, and security surface that the product does not need for
  an overview.
- **Derive cooperation from provider interaction metadata**: rejected; that
  metadata is content-free and not attributable to agent pairs, so links would
  imply false precision.
- **Web or pixel canvas**: rejected; the product is a text-only terminal
  application and ADR-0038 fixes `ratatui` as the presentation stack.
